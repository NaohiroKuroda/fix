# 【支払】部長承認 詳細設計書

> 共通の仕組み（ヘッダー / フィルタ / やり取り / iframe / テーマ / 送信・エラー方針）は
> [共通仕様_詳細設計.md](./00_共通仕様_詳細設計.md) を参照。本書は本画面固有の差分を記述する。

## 1. 概要

- **画面名**: 【支払】部長承認【業者選定済→FELIX(建設部)】
- **mode**: `manager-approval`
- **操作ロール**: 建設部部長、建設承認、administrator
- **目的**: 担当が選定・確定した見積先（担当承認済＝`APPLIED`）を部長が承認する。
  承認すると部長承認済（`APPROVED`）へ進む。妥当でない場合は**否認**して業者選定へ差し戻す。

業務フロー上の位置づけ:

```
業者選定 ──▶【部長承認】──承認──▶ 部長取消申請 ──▶ 部長取消承認
   ▲            │
   └──否認──────┘（DRAFT へ差し戻し・理由は「【否認】」コメントに記録）
```

## 2. 機能説明

本画面の操作は、**画面上部の「絞り込み・操作バー」のボタン**と、**明細（各行）のボタン**の
2つのボタン群から行う。以下ではボタンごとに実行される処理を分けて記載する。

前提となる一覧表示: 担当承認済（`APPLIED`）で部長承認待ちの見積先を「実行予算 → 項目 →
見積先」の明細で一覧表示する。見積額は確定見積を表示する。（→ §4, §5）

### 2.1 絞り込み・操作バーのボタン（画面上部）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 絞り込み（検索） | 実行予算名 / 項目名 / 見積先名でサーバ側フィルタし、一覧を再取得する。 | 共通仕様 §3 |
| コメント有無フィルタ | 全て / コメントあり / コメントなしでサーバ側フィルタする。 | 共通仕様 §3 |
| 明細を全て開く / 閉じる | 全実行予算カードの明細を一括で開閉する。 | §5 |
| 全て承認 / 全ての承認を解除 | 表示中の未処理行の承認選択を一括で ON / OFF する。 | §6.1 |
| 部長承認 | 選択した見積先を一括承認する。felix_total の建設部選定処理を呼び出して実行する。 | §6.1 |

> 本画面では相見積の回答有無で絞る「回答状態フィルタ」は表示しない。

**検索項目（絞り込み検索フォーム）**: 下記3項目を入力し「絞り込み検索」ボタンで送信すると、
条件に一致する一覧をサーバから再取得する。いずれも**部分一致（LIKE）**で、空欄の項目は条件から除外する。

| 入力欄（画面ラベル） | 検索対象 | 条件 |
| --- | --- | --- |
| 物件名 | 実行予算名（`t_buildings.building_name`） | 部分一致 |
| 項目名 | 費用項目名（`t_building_budget_items.item_name`） | 部分一致 |
| 見積先 | 見積先の会社名（`company_name`） | 部分一致 |

### 2.2 明細のボタン（各行）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 承認（選択トグル） | その見積先を承認対象として選択する。承認は上部の「部長承認」で一括実行。処理済みは「承認済」バッジ。 | §6.1 |
| 否認 | 否認理由モーダルを開き、1件ずつ業者選定へ差し戻す（`DRAFT` へ）。 | §6.2 |

| 見積先の詳細（会社名リンク） | felix_total の見積先編集画面を iframe モーダルで開く。 | 共通仕様 §5 |

- 対象ステータス: `approval_status = APPLIED`（担当承認済＝業者選定確定・部長承認待ち）。

## 6. 操作仕様

### 6.1 承認（pick-button・一括）

- 未処理（`approved=false`）行をボタンで選択（`checked`）。処理済みは静的バッジで再操作不可。
- ヘッダーの一括アクションで、選択した `partnerIds` をまとめて承認する。
- 活性条件: 1件以上選択あり。「全て承認／全ての承認を解除」で一括選択も可能。

入力: `PayablePartnerActionRequest`
- `partnerIds`: required / array / min:1
- `partnerIds.*`: integer / distinct / `exists:t_payable_partners,id`

felix_total 連携（`recordManagerApprovals`）:
処理順は業者選定（`02_支払_業者選定_詳細設計.md` §7.2）と同じ **「新テーブルを更新 → 現行 API」** で、
1トランザクションにまとめる（`syncWithFelixTotal()`）。

1. 見積先を旧 ID へ写像し、移行元（`source_id`）の無い行は除外する。
2. `approval_status = APPLIED` の行だけを対象に絞る
   （`CANCEL_APPLIED` / `CANCELLED` を巻き戻さないための from 状態ガード）。
3. `approval_status` を `APPLIED → APPROVED` へ UPDATE する。
4. 対象行につき `FelixTotalQuoteRequestGateway::tmpSelectCompany($unit, $company)` を呼ぶ
   （felix_total の `update_tmp_company_select_flg`＝建設部選定 相当）。
5. felix_total が失敗した場合は 3 の UPDATE をロールバックする。

戻り値は 3 で実際に遷移した件数。

- 部長ロール（`engineer_manager`）は felix_total 側の権限（`admin_role_permissions`）が必要。
  未付与だと laravel-admin が権限エラー画面（HTTP 200 の HTML）を返し、承認が反映されない
  （`felix_total/database/migrations/2026_07_22_150000_grant_admin_permission_to_engineer_manager_role.php` で付与）。

応答:
- 成功: `back()->with('success', "部長承認を実行しました。（n件）")`。
- 0件: `back()->with('error', '部長承認を実行できませんでした。対象の見積先をご確認ください。')`。

### 6.2 否認（業者選定へ差し戻し）★本画面固有

「否認」列のボタン → 理由入力モーダル → 1件ずつ差し戻す（1件処理）。
否認ボタンは**操作できる行（`operable`）にだけ出す**（それ以外は「—」）。

> 否認列・否認モーダルはモード設定 `PayableModeConfig.reject`（`hint` / `modalTitle` / `description`）で
> 共通化しており、【支払】部長取消承認と同じ UI を使う（→ [05_支払_部長取消承認](./05_支払_部長取消承認_詳細設計.md) §6.5）。

- 入力: `RejectPayableRequest`（部長取消承認の否認と共用）
  - `partnerId`: required / integer / `exists:t_payable_partners,id`
  - `reason`: required / string / max:1000（**否認理由は必須**）
- 処理: `ManagerApprovalService::reject()`
  1. `PayableRepository::rejectManagerApproval()`:
     承認・選定と同じく **「新テーブルを更新 → 現行 API」** を1トランザクションで行う。
     1. `APPLIED` の行のみ `approval_status = DRAFT` へ UPDATE（理由は列に持たず、コメントへ投稿）
        （`APPLIED` 以外は更新しない）。
     2. `FelixTotalQuoteRequestGateway::cancelAdoption($unit, $company)` を呼ぶ
        （felix_total の `update_adoption_flg` を `mode='false'` で実行＝採用取消）。
        現行側は `adoption_flg=0` / `company_select_flg=NULL` とし、`estimate_units.vendor_id` を NULL・
        `price` を再計算して業者選定前の状態へ戻す。
     3. felix_total が失敗した場合は 1 の UPDATE をロールバックする。
     4. 移行元（`source_id`）の無い見積先は現行 API を呼べないため、新テーブルのみ差し戻す。
  2. 差し戻し成功時、対象見積先が属する項目のコメントスレッドへ
     `【否認】{理由}` を部長発言として自動投稿（`CommentService::post()`）。
- 応答:
  - 成功: `back()->with('success', '否認しました。業者選定へ差し戻しました。')`。
  - 0件: `back()->with('error', '否認できませんでした。対象の見積先をご確認ください。')`。
- 差し戻された見積先は業者選定画面に `denied=true` で現れ、ボタンが赤表示になる（共通仕様 §6）。

否認モーダル UI:
- ゴールドではなく赤系の配色。理由未入力・送信中は「否認する」を無効化。
- 見積先名を明示し、「業者選定へ差し戻します」と案内する。

## 7. 共通機能の利用

- **やり取り（コメント）**: 全画面共通。**部長（manager）視点で発言**（共通仕様 §4）。
  業者選定画面の担当と同じ項目スレッドを共有し、否認理由もこのスレッドに記録される。
- **iframe モーダル**: 「見積先の詳細」（会社名リンク）（共通仕様 §5）。
- **フィルタ**: `keyword` / `itemLabel` / `vendor` / `comment`（`answer` は未使用）（共通仕様 §3）。

## 7.4 画面の表示条件

> 出典: **見積管理_処理フロー**（H列 初期表示条件 / I列 絞り込み条件 / J列 表示承認ステータス /
> K列 ステータス外表示形式 / L列 業者マイページ）。

### 初期表示条件

- 区分が**支払**
- **選定済み**

### 絞り込み条件

> 表の見方（処理フロー I列の記法）
> - **単一選択**（`・` 区切り）… セグメント／ラジオ。**初期値**の列が画面初期表示時の選択。
> - **チェックボックス**（`・` 区切りなし）… 単独のトグル。**初期値**が ON のものは初期表示時からチェック済み。

| 項目 | 形式 | 選択肢 | 初期値 |
| --- | --- | --- | --- |
| 区分 | 単一選択 | 全て / 支払 | **支払** |
| 回答状態 | 単一選択 | 全て / 見積回答あり / 見積回答なし | **全て** |
| 仮選定のみ表示 | チェックボックス | — | OFF |
| 未承認 | チェックボックス | — | **ON** |
| コメント | 単一選択 | 全て / コメントあり / コメントなし | **全て** |

> **現行実装との差異**: 本画面は現在コメントフィルタしか出していない
> （回答状態・仮選定のみ表示・未承認は未実装）。§2.1 の「本画面では回答状態フィルタを表示しない」も
> 処理フローに合わせて見直すこと。


> **区分の切り替え**
> - **支払**（初期値）… `t_payable_partners` の取引先だけを表示する。
> - **全て** … 支払に加えて `t_billing_partners`（請求）の取引先も**同じ一覧に並べる**。
>   請求行は承認ステータスに関わらず**表示のみ**で操作できない（サーバが `operable = false` を返す）。
>   また **絞り込みはすべて支払（自区分）の行にのみ適用**し、請求行は絞り込まない。
>   自区分にヒットが無い項目は請求行ごと非表示になる（共通仕様 §3.3）。

### 表示する承認ステータス

| ステータス | 意味 |
| --- | --- |
| `APPLIED` | 申請中（承認待ち） |

### 表示ステータス以外のデータの扱い

| ステータス | 挙動 |
| --- | --- |
| `APPROVED`（承認済） | 承認・否認できない |
| `CANCEL_APPLIED`（取消申請中） | 承認・否認できない |
| `CANCELLED`（取消承認済） | 承認・否認できない |

### 業者マイページ側の操作

**発注書を確認し、「請負承認」ボタンを押す。**
現行 felix_total と同じ仕組み（`orders.adoption_flg` / `adoption_date` に記録）。

## 7.5 操作 → データ更新先

> 出典: **見積管理_処理フロー**（G列「データ更新先」）。
> 表の「更新先」はスプレッドシートの記述をそのまま構造化したもの。現行実装との差異は下の注記に記す。

| 操作 | 更新先 |
| --- | --- |
| **承認** | 発注書を作成し、業者マイページに表示<br>**支払発注（`t_payable_orders`）に登録** ※新テーブルの作成待ち<br>支払取引先（`t_payable_partners`）の承認ステータスを更新（`APPLIED` → `APPROVED`） |
| **否認** | 選定が解除される（業者選定へ差し戻し）<br>支払取引先（`t_payable_partners`）の承認ステータスを更新（`APPLIED` → `DRAFT`）<br>コメント（`t_comments`）に登録 |

**現行実装との差異**

- **`t_payable_orders` はテーブル自体が未作成**（新テーブルの作成待ち）のため、発注レコードの登録・発注書の作成は未実装。
  現行は felix_total の建設部選定（`update_tmp_company_select_flg`）を呼ぶのみ（§6.1）。
- 否認時のコメント登録（`【否認】{理由}`）は実装済み。否認理由の専用列は新スキーマに無いため、
  このコメントが唯一の記録になる（§6.2）。

## 8. 留意事項

- 承認（felix_total 経由・トリガー同期）と否認（新スキーマ直接 UPDATE）で反映経路が異なる点に注意。
- 否認は必ず理由を残し、コメントスレッドへ痕跡が残る（担当が差し戻し理由を確認できる）。
