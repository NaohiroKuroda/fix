## 0. 前提

もらいは「**業者と金額のすり合わせが TEL で完了済み**」で始まるため、相見積・業者選定が発生しない。
画面とデータの向きは、はらい（支払）と同じ **FELIX → 業者** に揃え、**見積も発注も FELIX 側で自作自演で登録**する。
業者マイページ側は「内容を確認して承諾する」だけになる（フロー図 凡例「もらい(Fix)」）。

### 対象テーブル

| テーブル | 用途 | 旧（felix_total）の対応 |
| --- | --- | --- |
| `t_billing_partners` | 請求取引先（もらいの業者） | `estimate_unit_companies`（`invoice_flg = 1`） |
| `t_billing_quotations` | 請求見積（版管理。`is_latest`） | `estimate_unit_company_files` |
| `t_billing_quotation_details` | 請求見積明細 | `estimate_unit_company_file_units` 相当 |
| `t_billing_orders` | 請求発注（発注書） | 対応なし（新規） |
| `t_billing_order_details` | 請求発注明細 | 対応なし（新規） |
| `t_comments` / `t_comment_read_timestamps` | やり取り（項目単位・支払と共通） | なし |

> 建物・項目（`t_buildings` / `t_building_budget_items`）は支払と共通。**請求専用ではない**が、
> 請求取引先の親になるため、同期の前提として本書にも含める。

### 凡例

- **CRUD**: C=登録 / R=参照 / U=更新 / D=削除（論理削除を含む）
- **状況**: ✅実装済み ／ 🔺暫定・部分実装 ／ ❌未実装 ／ ⏸一次リリース対象外
- **担当**: 新Fix＝このリポジトリ（`fix`） ／ 現行Fix＝`felix_total` 管理画面 ／ 業者MP＝業者マイページ（felix_total）

## B. 現行Fix（felix_total）側の操作で必要な請求系新テーブル CRUD

> **2026-08-31 対応済み**: 現行Fix の同期サービス `NewQuotationRegisterService` が
> `estimate_unit_companies.invoice_flg` で登録先を振り分けるようになった（`upsertPartner()`）。
> `invoice_flg = 1` → `t_billing_partners` ／ `0` → `t_payable_partners` へ `source_id` で突合して INSERT/UPDATE する。
> 「請求先にする」を切り替えた場合は、**以前に登録した反対側のレコードを論理削除**し、戻したときは復活させる。
> 振り分けは実行予算の新規作成・更新・項目追加・見積業者フォームの保存の**4経路すべて**で効く。
>
> 残る穴は **B-4（業者そのものの削除）／ B-6（新→旧の同期 API）／ B-7（既存データの移行）**。

### F-3. 送信処理の仕様（共通）

1. **呼び出し経路**: 新Fix（見積承認 / ⑧ の内部処理）→ `BillingNotificationMailService` →
   `SendMailService::enqueue()` → `MailQueueRepository` → `mail_queues`（別DB `itplus4_list`）。
   **felix_total を経由しない**（同じキューへ積むので配信経路・送信履歴は現行と1本のまま）。
2. **粒度**: 引数は請求取引先ID（`t_billing_partners.id`）の配列。現行側で `source_id`（= `estimate_unit_companies.id`）へ変換し、会社単位にグルーピングする。
   `source_id` が無い（移行元の無い）取引先は**送信対象外**とし、件数に数えない（見積依頼と同じ扱い）。
3. **トークン**: `EC::create_token($company_id)` を使う。会社ごとに使い回しで、無ければ発行する。
4. **送信予約**: `send_time = 現在 +10分` / `status = 0`。即時送信はしない（既存踏襲）。
5. **失敗時**: メール送信の失敗で**承認そのものは巻き戻さない**。承認（ステータス更新・発注書発行）をコミットしたあとに送信を試み、失敗はログとトースト（「承認しましたが通知メールの送信に失敗しました」）で知らせる。
   → 送信のリトライ手段（再送ボタン）を持つかは §D-8。
6. **重複送信**: 同じ請求取引先へ短時間に複数回送らないよう、送信履歴（F-4）の有無で抑止する。
   ただし**否認 → 再申請 → 再承認**では再送する（履歴は積む）。
7. **テスト送信**: 既存の `$no_send` 相当（宛先を固定アドレスに差し替える）を、環境変数で切り替えられるようにする。
