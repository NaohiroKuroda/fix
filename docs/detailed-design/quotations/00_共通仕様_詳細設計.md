## 0. 承認ステータス（`approval_status`）

支払（`t_payable_partners`）／請求（`t_billing_partners`）で**同じ語彙**を使う。
値は **見積管理_処理フロー（J列）を正**とする。

| 値 | 意味 | 主な遷移契機 |
| --- | --- | --- |
| `DRAFT` | 未申請 | 業者追加の直後 / 否認・取消承認による差し戻し |
| `APPLIED` | 申請中（承認待ち） | 支払＝業者選定の確定 / 請求＝承認申請 |
| `APPROVED` | 承認済（承認完了） | 部長承認（支払＝部長承認 / 請求＝見積承認） |
| `CANCEL_APPLIED` | 取消申請中（取消承認待ち） | 取消申請 |
| `CANCELLED` | 取消承認済（取消承認） | 取消承認 |

各画面は「**表示する承認ステータス**」で一覧を絞り、それ以外のステータスは
画面ごとに「出すが操作させない」か「出さない」かを決める（各書の §7.4 / §8.4）。

> **コード・DB は未追随**。現在の実装と DB のデフォルトは `UNSELECTED` / `STAFF_APPROVED` /
> `APPROVED` / `CANCEL_APPLIED` / `CANCEL_APPROVED`。対応は
> [`backend.md` §3.7](../../architecture/backend.md) を参照。

## 1. 共通コンテナ（PayableScreen.vue）

各画面ページ（`pages/quotation/payable/<kebab>/ui/<Pascal>Page.vue`）は、共通コンテナに props を渡すだけの薄いラッパーである。

### 1.1 受け取る props

| prop | 型 | 説明 |
| --- | --- | --- |
| `title` | `string` | 画面タイトル（例: 見積依頼） |
| `statusLabel` | `string` | 状態ラベル（例: 【FELIX→業者依頼前】） |
| `mode` | `PayableMode` | 画面モード。列・操作の出し分けに使う |
| `actionLabel` | `string \| null` | ヘッダー一括アクションのボタン名（取消系は使わない） |
| `glass` | `boolean` | リキッドグラス配色を使うか（全画面 `true`） |
| `projects` | `PayableProject[]` | 案件→項目→見積先のフラット行（サーバから） |
| `pagination` | `PayablePagination` | ページネーション情報 |
| `filters` | `PayableFilters` | 現在の絞り込み条件（画面再表示用） |

### 1.2 モード定義（`PAYABLE_MODE_CONFIG` / `lib/quotation-management.ts`）

各 `mode` は最終列のラベル・操作種別・処理済み判定を持つ。操作種別（`kind`）は3種類。

| kind | 画面 | 挙動 |
| --- | --- | --- |
| `checkbox` | 見積依頼 | 未依頼行をチェックで選び、ヘッダーの送信ボタンで一括確定 |
| `toggle-button` | 業者選定 | サーバの選定状態を初期値に、押下でトグル（選び替え）。ヘッダーの確定で送信 |
| `pick-button` | 部長承認 / 取消申請 / 取消承認 | 未処理行を選ぶ。承認は一括、取消系は1件ずつ理由モーダル |

主なフィールド: `columnLabel`（最終列名）、`showQuote` / `quoteColumnLabel`（見積額列）、
`appliedKey`（処理済みを表すサーバ側 boolean）、`reselectable`（処理済みでも再操作可＝見積依頼のみ）、
`idleLabel` / `activeLabel` / `appliedLabel`、`processingLabel`、`hint`、`bulkSelectLabel` / `bulkClearLabel`
（任意。未指定の画面＝業者選定では一括選択ボタンを出さない）。

### 1.2.1 見積額列（`showQuote` / `quoteColumnLabel`）★重要

**相見積・確定見積・見積額のいずれも、対応するテーブルの `amount_excluding_tax`（税抜）を表示する。**

| 画面 | 見出し | 値 |
| --- | --- | --- |
| 見積依頼 / 業者選定 | 相見積 | その見積先の最新見積（`t_payable_quotations` の `is_latest`）の `amount_excluding_tax` |
| 部長承認 / 部長取消申請 / 部長取消承認 | 確定見積 | **選定済みの見積先**の最新見積の `amount_excluding_tax`（項目単位・同一項目の全行に同じ値） |
| 発注管理（業者承諾確認ほか） | 見積 / 相見積 | その見積先の最新見積の `amount_excluding_tax` |
| 【請求】各画面 | 見積額 / 確定見積 | `t_billing_quotations` の最新版の `amount_excluding_tax`（**金額のみ**。見積日は一覧に出さず、見積モーダルで確認する） |

**確定見積の求め方**（`PayableRepository::settledQuoteMap()`）

- 対象は**選定済み**（`approval_status <> 'DRAFT'`）の支払見積先。その最新見積の `amount_excluding_tax`。
- 一覧の絞り込み（見積先名・ステータス）で選定済みの行が表示対象から外れていても拾えるよう、
  表示中の**項目 ID から引き直す**。同一項目に選定済みが複数あるときは最小 ID の行を採用する
  （業者選定は1業者が前提。旧 felix_total の `adoption_flg=1` に相当）。
- 選定済みの見積先が無い項目は `null`（画面は「—」）。まだ確定していないことを正しく表す。

> **`t_building_budget_items.quotation_amount` は使わない。** 同列は felix_total の実行予算画面で
> 保存し直したときにだけ同期される（丸めた）コピーで、fix 側で業者選定を確定しても更新されない。
> そのため未同期のまま空になったり、未選定の項目に古い値が残ったりして実データとズレる。

### 1.3 行キー（`payableRowKey`）

明細行の一意キー。取引先ありは**区分＋id**（支払 = `c{partnerId}` / 請求 = `b{partnerId}`）、
取引先なしは `u{budgetItemId}`。v-for のキーと選択状態のキーに共用する。
選択・選定・仮選定などのローカル状態はすべてこのキーで管理する。

> **区分を先頭に付けるのは必須。** 支払は `t_payable_partners`、請求は `t_billing_partners` と
> 別テーブルで id が独立採番のため、区分フィルタ「全て」で両方を並べると id が衝突しうる。
> 衝突すると v-for のキーが重複して行の描画が壊れ（クライアント側の絞り込みで消えたまま戻らない）、
> さらに選択状態が支払行と請求行で混線する。
> 請求系画面（`BillingScreen`）も同じ理由で `billingRowKey`（`b{partnerId}` / `c{partnerId}`）を使う。

### 1.3.1 選択・送信の対象は自区分の行だけ

区分フィルタ「全て」では逆区分の取引先も同じ一覧に並ぶが、**操作できるのは画面の区分側だけ**
（サーバが `operable=false` を返す）。支払系画面の選択・選定・確定送信の判定は、
`billingTarget=false` の行（`payableRows`）だけを対象にする。逆区分の行を混ぜると、
別テーブルの id を支払側のエンドポイントへ送ってしまう。

### 1.4 明細の開閉

案件カード単位で開閉（既定は開）。ヘッダー下の「明細を全て開く／閉じる」で一括トグルできる。

## 2. ヘッダー（固定）

`sticky top-0` で最上部に固定される。構成要素:

1. **タイトル + 状態ラベル**（例: 見積依頼　状態：【FELIX→業者依頼前】）
2. **一括アクションボタン**（`actionLabel` があり、かつ取消系でない画面のみ）
   - 活性条件（`actionEnabled`）:
     - `pick`/`checkbox`: 1件以上チェックあり（`anyChecked`）
     - `toggle`（業者選定）: サーバ状態から変更（押下）があり、かつ選定が1件以上（`vendorDirty && size>0`）
   - 送信中は `processingLabel` を表示し無効化。選択件数を `（n）` で併記。
3. **絞り込みバー**（`QuotationFilterBar`）

ヘッダー下（スクロール本体の先頭）に操作行:
- 明細を全て開く／閉じる
- 全て選択／全て解除（`bulkSelectLabel` / `bulkClearLabel`。取消系および業者選定は非表示）
- 回答状態フィルタ（見積依頼 / 業者選定のみ）
- 仮選定のみ表示 / 未依頼のみ表示（見積依頼のみ）
- コメント有無フィルタ（全画面）
- ページャ（上下2箇所）

**ページネーション（1ページの表示件数）**: 1ページあたり **10 案件（実行予算＝`t_buildings` 単位）** を表示する
（`AbstractPayableScreenController::PER_PAGE = 10`。全画面共通）。ページ送りは操作行と一覧末尾の
上下2箇所に `QuotationPager` を配置する。

- 表示件数の単位は**案件（実行予算）**であり、見積先（行）単位ではない。1案件が複数の項目・見積先を
  持つ場合、画面に並ぶ明細行数は10行より多くなる。
- サーバは `LengthAwarePaginator` で `currentPage` / `lastPage` / `perPage`（=10）/ `total` / `from` / `to`
  を返し、`PayablePagination` として画面へ渡す。

## 3. 絞り込み（フィルタ）

### 3.1 サーバ側フィルタ（`QuotationFilterBar` → GET リロード）

`QuotationManagementRequest` が受け取り、`PayableRepository::forPayableManagement()` で適用する。

| パラメータ | 対象 | 適用 |
| --- | --- | --- |
| `keyword` | 案件名（`building_name`） | LIKE 部分一致 |
| `itemLabel` | 項目名（`item_name`） | LIKE 部分一致 |
| `vendor` | 見積先名（`company_name`） | LIKE 部分一致（`whereHas('company')`） |
| `answer` | 回答状態（`all` / `answered` / `unanswered`） | 最新相見積履歴（`is_latest`）の有無。見積依頼・業者選定のみ |
| `comment` | コメント有無（`all` / `has` / `none`） | 項目のコメント有無（`whereHas('comments')`）。全画面 |
| `kind` | 区分（`all` / `payable` / `billing`） | 一覧に並べる取引先の区分。支払系画面の既定は `payable` |
| `page` | ページ番号 | ページネーション |

- 既定値（`all` / 空）は URL から省略する。
- フィルタ変更・検索・ページ移動はいずれも `router.get()` による部分再取得で、`preserveState` /
  `preserveScroll` を用いてローカル状態とスクロール位置を維持する。

### 3.2 クライアント側フィルタ

`displayProjects` で行を絞る（サーバ再取得なし）。画面ごとに次のチェックボックスを出す。

| 画面 | フィルタ | 条件 | 初期値 |
| --- | --- | --- | --- |
| 見積依頼 | 仮選定のみ表示 | `provisional` | OFF |
| 見積依頼 | 未依頼のみ表示 | `sendCount === 0` | **ON** |
| 業者選定 | 業者未選定 | `operable` | **ON** |
| 部長承認 | 未承認 | `operable` | **ON** |
| 部長取消申請 | 申請可能 | `operable` | **ON** |
| 【請求】見積作成 | 作成可能 | `operable` | **ON** |
| 【請求】見積承認 | 見積作成ずみ | `quotationAmount !== null` | **ON** |
| 【請求】見積承認 | 未承認 | `operable` | **ON** |
| 【請求】見積取消申請 | 申請可能 | `operable` | **ON** |
| 【請求】見積取消承認 | 承認可能 | `operable` | **ON** |

すべて OFF なら全件表示。詳細は各画面の設計書を参照。

#### 「この画面で操作できる行だけ」フィルタ（`operableFilterLabel`）

上表のうち `operable` を条件とするものは**同じ 1 つのチェックボックス**で、文言だけがモード設定
（`PayableModeConfig` / `BillingModeConfig` の `operableFilterLabel`）で切り替わる。

- **初期表示は常に ON**。その画面で着手すべき行（処理フロー J列の対象ステータス）だけを最初に見せる。
- **チェックを外すと全件表示**に戻る（他ステータスの行も並ぶが、操作はできない＝K列）。
- `operableFilterLabel` を持たない画面（見積依頼 / 【支払】部長取消承認 / 【請求】発注書確認）
  にはこのチェックボックスを出さない。【支払】部長取消承認は一覧そのものを対象ステータスで絞るため不要。

#### 否認（却下）列（`reject` / `rejectUrl`）

明細の右端に赤系の「否認」ボタンを出す画面がある。**操作できる行（`operable`）にだけ**表示し、
押下で否認理由モーダル（理由必須・最大1000字）を開いて1件ずつ実行する。
否認理由は項目のコメントスレッドへ `【否認】{理由}` として自動投稿される。

| 画面 | 否認の意味 | ステータス遷移 |
| --- | --- | --- |
| 【支払】部長承認 | 業者選定へ差し戻す | `APPLIED` → `DRAFT` |
| 【支払】部長取消承認 | 取消を却下して据え置く | `CANCEL_APPLIED` → `APPROVED` |
| 【請求】見積承認 | ③ 見積作成へ差し戻す | `APPLIED` → `CANCELLED` |
| 【請求】見積取消承認 | ③ 見積作成へ差し戻す | `CANCEL_APPLIED` → `CANCELLED` |

> 請求（もらい）は業者選定が無いため、否認の差し戻し先はどちらも **③【請求】見積作成**。
> 同画面は `DRAFT` / `CANCELLED` を操作対象にするので、`CANCELLED` にすれば同画面へ戻る。

支払系は `PayableModeConfig.reject`（`hint` / `modalTitle` / `description`。送信先は画面側で mode 分岐）、
請求系は `BillingModeConfig.reject`（`url` / `hint` / `modalTitle` / `description`）を持つ画面だけが否認列を出す。
入力は支払系が `RejectPayableRequest`（`partnerId` / `reason`）を2画面で共用、
請求系は `BillingReasonActionRequest`（`partnerIds` / `reason` 必須）。

### 3.3 区分「全て」のときの絞り込み適用範囲 ★重要

区分を「全て」にすると逆区分の取引先も同じ一覧に並ぶが、逆区分は**表示のみ**であって作業対象ではない。
そのため、**サーバ側・クライアント側を問わず、取引先レベルの絞り込みはすべて自区分の行にだけ適用する**。

| 対象 | 適用範囲 |
| --- | --- |
| 案件名（`keyword`）・項目名（`itemLabel`）・コメント有無（`comment`） | 案件／項目レベル。区分に依らず適用 |
| 見積先名（`vendor`）・回答状態（`answer`）・画面の初期表示条件（`MODE_OPERABLE_STATUS` ほか） | **自区分の取引先のみ** |
| クライアント側フィルタ（§3.2 のチェックボックス） | **自区分の行のみ** |

項目・案件を出すかどうかも**自区分の絞り込み結果で決める**。自区分にヒットが 1 件も無い項目は、
逆区分の行ごと非表示にする（絞り込みが一覧を狭める効果を保つため）。逆区分の行は、
絞り込み後に自区分の行が残った項目にだけ、絞り込まずそのまま並べる。

実装:

- サーバ（`PayableRepository`）… `$filterRelation`（自区分のリレーション）にだけ絞り込みを適用し、
  逆区分は素通し。項目の存在判定（`applyItemFilter` の `whereHas`）も `$filterRelation` のみで行う。
  自区分が一覧に出ない（`kind` が逆区分のみ）ときだけ、表示している側に適用する。
- クライアント（`PayableScreen` / `BillingScreen`）… 自区分の行に行フィルタを適用し、
  残った行の項目（支払系は `budgetItemId` / 請求系は `itemName`）に属する逆区分の行だけを無条件で並べる。
- 請求系（`BillingMockService`）も自区分＝請求で同じ扱い。

## 4. やり取り（コメント / チャット）機能 ★全画面共通

見積についてのやり取りを LINE 風モーダルで行う。担当（staff）と部長（manager）が同じ項目について
コメントを交わす。否認・取消申請・取消承認の理由も、このスレッドへ自動で記録される。

**支払系・請求系の全画面で同じ仕組み**を使う。スレッドは項目単位なので、
**同じ項目なら支払画面から開いても請求画面から開いても同じ内容**が見える。

### 4.1 データ構造

- コメントは**費用項目（`t_building_budget_items`）単位**でポリモーフィックに集約する
  （`commentable_type = App\Models\TBuildingBudgetItem` / `commentable_id = 項目ID`）。
  項目に見積先が複数あっても1スレッドにまとまる。
- ルートは取引先でバインドし、コントローラが `building_budget_item_id` へ読み替えてスレッドを引く。
  支払＝`t_payable_partners`（`{quotation}`）、請求＝`t_billing_partners`（`{partner}`）。
- 添付は `t_attachments` にポリモーフィックで紐づき、`public` ディスクの `comments/{itemId}/` に保存。
- 既読は `t_comment_read_timestamps`（`readable_type` / `readable_id` / `user_id` / `last_read_at`）で管理。

### 4.2 API（`PayableMessageController` / `BillingMessageController`）

| メソッド | ルート名 | 内容 |
| --- | --- | --- |
| GET | `quotation-management.payable-messages.index` | **支払**：項目の全コメントを古い順で返す（JSON）。開いた時点でログインユーザーの既読を「今」で更新 |
| POST | `quotation-management.payable-messages.store` | **支払**：コメント1件を投稿（本文・添付いずれか必須）。投稿者＝ログイン中 admin |
| GET | `quotation-management.billing-messages.index` | **請求**：同上（`t_billing_partners` でバインド） |
| POST | `quotation-management.billing-messages.store` | **請求**：同上 |

どちらも `CommentService`（項目 ID ベース）を共用するため、処理内容は同一。
入力（`StoreCommentRequest`）・添付の扱いも共通。

投稿の入力（`StoreCommentRequest`）:
- `body`: 任意。ただし `files` が無ければ必須（`required_without:files`）、最大2000文字。
- `files`: 任意、最大 **5 件**。1件あたり最大10MB（`files.*`: `file`, `max:10240`）。
  加えて拡張子ホワイトリスト（`extensions:...`）で許可形式のみ受け付ける。
  上限・許可拡張子・画像圧縮・サムネイルの詳細は
  [99_添付ファイル_詳細設計.md](./99_添付ファイル_詳細設計.md) を参照。

添付ファイル配信（`CommentAttachmentController`）:
- `thumb`（`...comment-attachments.thumb`）: 認証付きインライン配信（**画像サムネイルのみ**）。
- `download`（`...comment-attachments.download`）: 端末へダウンロード（元ファイル名）。全ファイル共通のクリック先。
- 公開ストレージの静的配信は Web サーバ設定依存で 403 になり得るため、Laravel から直接ストリームする。
- インライン配信はサムネイル画像に限定し、SVG/HTML 等はインライン配信しない（XSS 対策）。

### 4.3 UI 仕様（`shared/ui/comment-thread/CommentThreadModal.vue`）

モーダル本体は**共通コンポーネント**で、支払系（`PayableScreen`）と
請求系（`BillingScreen`）の両方が使う。呼び出し側は「どのエンドポイントを叩くか」を
`index-url` / `store-url` で渡すだけで、取得・投稿・添付・エラー表示はコンポーネントが持つ。

> **区分「全て」のときの叩き先**: 行の `billingTarget` で切り替える
> （支払行＝`quotation-messages` / 請求行＝`billing-messages`）。
> 逆区分の行から開いても、項目が同じなら同じスレッドが見える。

- 起動: 明細の項目名の右隣にある吹き出しボタン（`open-chat`）。項目に見積先が複数あっても
  「表示中の先頭行」に1つだけ表示する。**未読数バッヂ**（`unreadCount`）を赤丸で重ねる（99超は `99+`）。
- コメントが1件以上ある項目（`hasComments`）は、吹き出しボタンを選定色（ゴールド）で強調する。
- モーダル: 自分の投稿は右寄せ・ゴールド吹き出し、相手は左寄せ・白吹き出し。役割バッジ（部長／部下）と
  投稿者名・時刻を表示。画像添付はサムネイル、その他はファイル名リンク（ダウンロード）。
- 入力: テキストエリア（Enter で送信、Shift+Enter 相当の改行は本文仕様に準拠）＋ファイル添付
  （ボタン選択 / ドラッグ&ドロップ）。送信可否は本文か添付のいずれかがあること。
- 発言ロール表示は `auth.user.isEstimateManager`（部長 / 部下）で決める。
- fetch は axios 非導入のため、`XSRF-TOKEN` クッキーを `X-XSRF-TOKEN` ヘッダへ手当てして送る。
- 送信成功時は一覧の「やり取り件数・コメント有無」を楽観的に更新し、開いた時点で未読バッヂを即時クリアする。

### 4.4 未読・件数のメタ付与

一覧取得時に各取引先へ以下を付与する（同一項目の各取引先へ同じ値）:
- `comments_count`（総数）/ `has_comments`（1件以上か）/ `unread_count`（最終既読より新しい他者コメント数）。

支払系は `PayableRepository::attachCommentMeta()`、
請求系は `BillingRepository::attachCommentMeta()` が付与する（実装は同一）。
モーダルが読む内容と件数バッジを食い違わせないため。

## 5. felix_total 連携用の iframe モーダル ★全画面（一部リンクは見積依頼のみ）

felix_total（laravel-admin）の画面を iframe で開く汎用モーダル。明細から `{ url, title }` を受け取り開く。
閉じたら一覧を部分再取得（`router.reload({ only: ['projects','pagination'] })`）して変更を反映する
（felix_total と同一 DB のため再取得で反映される）。

| リンク | config テンプレート | 置換 `{id}` | 出現画面 |
| --- | --- | --- | --- |
| 見積先の詳細 | `felix.vendor_detail_url` | 見積先 `source_id` | 全画面（会社名リンク） |
| 業者追加 | `felix.add_vendor_url` | 項目 `source_id` | 見積依頼のみ |
| 業者マイページ | `felix.estimate_edit_url` | 見積先 `source_id` | 見積依頼（別タブ `target=_blank`） |

URL が未設定（テンプレート空 or `source_id` なし）の場合、リンクは非表示またはプレーン表示にする。

## 6. 配色テーマ（`useQuotationTheme.ts`）

`glass=true` で「明細は白／それ以外はリキッドグラス（FELIX 紺 `#1e2a44` 系＋金 `#c4a35b`）」の配色を適用する。
背景に装飾ブロブ（ぼかし）を敷く。ボタンの2状態（淡色＝未操作 / ベタ塗り＝操作済）は全モードで統一。

ボタン状態色（`PayableProjectCard`）:
- **ゴールド（base）**: 通常。
- **緑（green）**: 仮選定済み、または否認差し戻しが同一項目のいずれかの選定で解消された。
- **赤（red）**: 否認で差し戻され、まだ同一項目のどの業者も選定されていない。

> Tailwind のクラス検出のため、色クラスは必ずリテラル文字列で保持する（動的生成しない）。

## 7. 送信・エラー処理の共通方針

- 送信は Inertia の `useForm`（`processing` 統合）＋ Wayfinder アクションで行う。成功時はサーバが
  `back()` で元画面へ戻し、一覧が再読込される。ローカルの選択・選定状態はクリアする。
- Service 層は各ユースケースを try/catch で囲み、例外時は `Log::error()` で記録のうえ
  `ServiceException` を投げる。`bootstrap/app.php` がこれを画面右上のトースト（`flash.error`）へ変換する。
- 処理件数が0件の場合、Controller は `back()->with('error', ...)`（想定内の失敗メッセージ）を返す。
- 成功時は `back()->with('success', "...（n件）")`。
- 入力バリデーションは各 FormRequest が担い、`partnerIds` は `distinct` + `exists` で検証する。
