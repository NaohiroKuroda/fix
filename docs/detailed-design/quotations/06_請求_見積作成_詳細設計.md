> [共通仕様_詳細設計.md](./00_共通仕様_詳細設計.md) を参照。本書は本画面固有の差分を記述する。
>
> 出典: [`docs/operations/もらい_運用フロー.drawio`](../../operations/もらい_運用フロー.drawio)（①〜③）／
> テーブル定義書（`t_billing_partners` / `t_billing_quotations` / `t_billing_quotation_details`）。
> ※ テーブル定義書の表記は `t_billing_quotation_ditails` だが、実 DB の物理名は

## 1. 概要

- **画面名**: 【請求】見積作成【FELIX(担当者)→業者】
- **区分**: 請求＝「もらい」（FELIX が請求する側のフロー）／**新規画面**
- **mode**: `billing-quote-create`
- **操作ロール**: 建設部担当者（`staff_role_slugs`）、administrator
- **目的**: もらい（請求先）として登録した取引先に対し、FELIX 側で**見積を代理作成**する。
  作成・保存すると部長承認待ち（`STAFF_APPROVED`）へ進む。

### 1.1 「もらい」の前提（重要）

- もらいレコードを作成する時点で、**業者と金額のすり合わせは TEL で完了している**。
  したがって**相見積・業者選定は発生しない**（業者から見積が返ってくるステップが無い）。
- 本来のもらいは「業者が発注者」だが、Fix では画面・データの向きを**はらい（支払）と同じ
  FELIX→業者に揃え**、見積依頼と発注を FELIX 側で**自作自演**で登録する。
  請求だけが FELIX→業者（＝FELIX が請求する側）になる。
- もらい／はらいの判定は現行 `estimate_unit_companies.invoice_flg`。
  新スキーマでは**テーブルごと分離**され、支払＝`t_payable_partners` / 請求＝`t_billing_partners` になる。

業務フロー上の位置づけ:

```
現行Fix 実行予算作成 ──実行予算データ──▶ ①【請求】見積作成（一覧表示）
現行Fix 項目追加     ──項目データ──────▶ ②業者追加（「請求先にする」ON＝もらい）
                                            │
                                            ▼
                              ③ 見積作成モーダル（見積額入力・保存）
                                            │
                                            ▼
                                  ④【請求】見積承認（部長）
```

取消承認された見積は本画面（③ 見積作成）へ差し戻される（→ [09_請求_見積取消承認](./09_請求_見積取消承認_詳細設計.md)）。

### 2.3 ② 業者追加（もらいとして登録）

- 追加は現行 felix_total の見積先追加画面（iframe）で行う。**「請求先にする」を ON** にした業者が
  もらい（請求）として登録される。現行の業者追加ページからでも、もらいの業者は追加できる。
- 追加された行は一覧に**「請求」区分**として表示される（区分バッジ。支払行と地色でも区別する）。
- iframe を閉じたら一覧を再取得して反映する（共通仕様 §5）。

## 6. ③ 見積作成モーダル（⭐️新規）

### 6.1 フロー

1. 明細行の「見積作成」ボタンを押す。
2. モーダルで見積日・明細・金額を入力する。
3. 「保存」で確定 → `t_billing_quotations`（＋明細）を作成し、`approval_status` を
   `UNSELECTED → STAFF_APPROVED` へ進める。
4. 一覧を再取得し、当該行は本画面の抽出条件から外れる（→【請求】見積承認へ）。

### 6.2 入力項目

**ヘッダー（`t_billing_quotations`）**

| 画面ラベル | カラム | 型 / 必須 |
| --- | --- | --- |
| 見積日 | `quotation_date` | DATE / 必須 |
| 合計金額（税別） | `amount_excluding_tax` | BIGINT / 必須（明細から自動計算・手入力も可） |
| 消費税調整 | `tax_adjust` | BIGINT / 既定 0 |
| 源泉所得税 | `withholding_income_tax` | BIGINT / 任意 |
| コメント | `comment` | TEXT |
| ファイルURL | `file_url` | VARCHAR(255) / 任意 |

**明細（`t_billing_quotation_details`）** ※行の追加・削除ができる

| 画面ラベル | カラム | 備考 |
| --- | --- | --- |
| メモ行 | `is_memo` | ON のとき項目名以外は NULL |
| 拠点 | `branch_code` | `constant.branch_list` |
| 部署 | `department_id` | `departments.id` |
| 項目名 | `name` | |
| 数量 | `quantity` | INT |
| 単位 | `unit_id` | `master_units.id` |
| 単価 | `unit_price` | BIGINT |
| 課税区分 | `tax_type` | `TAXABLE` / `NON_TAXABLE` |
| 消費税率 | `tax_rate` | DECIMAL(3,2)。**string のまま扱う** |
| 税込 | `is_tax_inclusive` | BOOLEAN |
| 金額 | `price` | 数量 × 単価（§6.4） |

### 6.3 処理（保存）

1. 同一 `billing_partner_id` の既存 `t_billing_quotations` を `is_latest = FALSE` に更新する。
2. 新しい `t_billing_quotations` を `is_latest = TRUE` で作成する。
3. 明細を `t_billing_quotation_details` へ一括作成する。
4. `t_billing_partners.approval_status` を `UNSELECTED → STAFF_APPROVED` へ更新する。
5. 1〜4 は 1 トランザクション（Service 層でトランザクション制御）。

> 見積は**版管理**（`is_latest`）とする。修正時は上書きせず新しい版を作る。

### 6.4 金額計算（BCMath 必須）

小数を含む計算（消費税率・按分など）は **`float` を使わず BCMath** で行う
（[`backend.md`](../../architecture/backend.md) §5.5、`App\Utils\Decimal` 経由）。

- 明細金額: `price = 数量 × 単価`（円未満は切り捨て）
- 税抜合計: `amount_excluding_tax = Σ price`（`is_tax_inclusive` の行は税抜へ換算）
- 消費税: `Σ(price × tax_rate)` を課税区分ごとに集計 → 円未満は四捨五入 → `tax_adjust` を加算
- `tax_rate` / `share` は **string 型のまま**取り扱う（テーブル定義書の実装メモに準拠）

### 6.5 応答

- 成功: `back()->with('success', '見積を作成しました。')`
- 失敗: `back()->with('error', '見積を作成できませんでした。')`
- 例外: `ServiceException` → トースト

## 8.5 操作 → データ更新先

> 出典: **見積管理_処理フロー**（G列「データ更新先」）。
> 表の「更新先」はスプレッドシートの記述をそのまま構造化したもの。現行実装との差異は下の注記に記す。

| 操作 | 更新先 |
| --- | --- |
| **業者追加** | 請求取引先（`t_billing_partners`）に登録 |
| **見積作成** | 請求見積（`t_billing_quotations`）と請求見積明細（`t_billing_quotation_details`）に登録 |
| **見積修正** | 請求見積明細（`t_billing_quotation_details`）に**登録か更新か未確定**（§9） |
| **承認申請** | 編集をロックして承認申請（「【請求】見積承認」画面に表示）<br>請求取引先（`t_billing_partners`）の承認ステータスを更新（`UNSELECTED` → `STAFF_APPROVED`） |

> **重要**: 「見積作成／修正」と「承認申請」は**別の操作**である。モーダルの保存だけでは承認待ちにならず、
> 明示的な承認申請で編集がロックされ、承認ステータスが `STAFF_APPROVED` へ進む。

**現行実装（モック）との差異**

- モックはモーダルの「保存」で承認申請まで済ませる想定で書かれている。
  実装時は **保存（何度でも可）→ 承認申請（1回・編集ロック）** の2段構えに分けること。
- 承認申請後の編集ロック（画面上の見積作成ボタンを不活性にする等）は未実装。

## 9. 留意事項・未確定事項

- **請求／支払のテーブル分割**: 2026-08 のスキーマ改訂で見積先は
  支払＝`t_payable_partners` / 請求＝`t_billing_partners` に分割された（旧 `is_billing_target` 列は廃止）。
  これに伴い**支払系5画面には請求（もらい）行が出なくなっている**。
  もらい運用フロー ⑦「業者選定画面にもらい行を表示のみで出す」を維持するかは**要確認**
  （維持する場合は支払画面側で両テーブルを UNION する実装が必要）。
- **承認ステータス**: `UNSELECTED` / `STAFF_APPROVED` / `APPROVED` / `CANCEL_APPLIED` /
  `CANCEL_APPROVED`（テーブル定義書に準拠）。支払側の実装も 2026-08 のスキーマ改訂でこの値に統一済み。
