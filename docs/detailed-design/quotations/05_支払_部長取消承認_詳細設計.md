# 【支払】部長取消承認 詳細設計書

> 共通の仕組み（ヘッダー / フィルタ / やり取り / iframe / テーマ / 送信・エラー方針）は
> [共通仕様_詳細設計.md](./00_共通仕様_詳細設計.md) を参照。本書は本画面固有の差分を記述する。

## 1. 概要

- **画面名**: 【支払】部長取消承認【FELIX(建設部部長)→FELIX(担当者)】
- **mode**: `cancel-approval`
- **操作ロール**: 建設部部長、建設承認、administrator
- **目的**: 担当が申請した取消（取消申請中＝`CANCEL_APPLIED`）を部長が**承認**または**否認**する。
  - **承認** … 設計部承認済（`CANCELLED`＝取消承認＝完了扱い）へ進む。
  - **否認** … 取消を認めず、部長承認済（`APPROVED`）のまま**据え置く**。
  いずれも理由の入力を必須とする。

業務フロー上の位置づけ:

```
… ──▶ 部長取消申請 ──▶【部長取消承認】──承認──▶ CANCELLED（完了）
                                   └──否認──▶ APPROVED のまま据え置き
```

## 2. 機能説明

本画面の操作は、**画面上部の「絞り込み・操作バー」のボタン**と、**明細（各行）のボタン**の
2つのボタン群から行う。以下ではボタンごとに実行される処理を分けて記載する。

前提となる一覧表示: 取消申請中（`CANCEL_APPLIED`）の見積先を「実行予算 → 項目 → 見積先」の明細で
一覧表示する。見積額は確定見積を表示する。本画面は**1レコードごとに理由入力モーダルで単体実行**する
方式のため、ヘッダーの一括アクションボタン・「全て選択」は出さない。（→ §4, §5）

### 2.1 絞り込み・操作バーのボタン（画面上部）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 絞り込み（検索） | 実行予算名 / 項目名 / 見積先名でサーバ側フィルタし、一覧を再取得する。 | 共通仕様 §3 |
| コメント有無フィルタ | 全て / コメントあり / コメントなしでサーバ側フィルタする。 | 共通仕様 §3 |
| 明細を全て開く / 閉じる | 全実行予算カードの明細を一括で開閉する。 | §5 |

> 本画面は per-row 方式（`isPerRowAction`）のため、「全て選択」「一括アクション」ボタン、
> および「回答状態フィルタ」は表示しない。

**検索項目（絞り込み検索フォーム）**: 下記3項目を入力し「絞り込み検索」ボタンで送信すると、
条件に一致する一覧をサーバから再取得する。いずれも**部分一致（LIKE）**で、空欄の項目は条件から除外する。

| 入力欄（画面ラベル） | 検索対象 | 条件 |
| --- | --- | --- |
| 物件名 | 実行予算名（`t_buildings.building_name`） | 部分一致 |
| 項目名 | 費用項目名（`t_building_budget_items.item_name`） | 部分一致 |
| 見積先 | 見積先の会社名（`company_name`） | 部分一致 |

### 2.2 明細のボタン（各行）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 取消承認 | 押下で理由入力モーダルを開き、理由を入力して1件ずつ取消を承認する（`CANCELLED` へ）。 | §6 |
| 否認 | 押下で否認理由モーダル（赤系）を開き、1件ずつ取消を却下する（`APPROVED` のまま据え置き）。 | §6.5 |
| やり取り（吹き出し） | 項目単位のコメントスレッドを開き、建設部メンバー⇔部長でやり取りする。未読バッヂ・添付に対応。 | 共通仕様 §4 |
| 見積先の詳細（会社名リンク） | felix_total の見積先編集画面を iframe モーダルで開く。 | 共通仕様 §5 |

## 6. 操作仕様（取消承認・1件ずつ理由必須）

### 6.1 フロー

1. 行の「取消承認」ボタン → 理由入力モーダルを開く（対象1件）。
2. 理由を入力し OK → `CancelActionRequest` を POST。
3. `CancelApprovalService::confirm($partnerIds, $reason)`。

### 6.2 入力（`CancelActionRequest`）

- `partnerIds`: required / array / min:1
- `partnerIds.*`: integer / distinct / `exists:t_payable_partners,id`
- `reason`: required / string / max:1000（**理由は必須**）

### 6.3 処理（`recordCancelApprovals`）

業者選定・部長承認（`02` §7.2 / `03`）と同じく **「新テーブルを更新 → 現行 API」** の順で、
1トランザクションにまとめる（`syncWithFelixTotal()`）。

1. 見積先を旧 ID へ写像し、移行元（`source_id`）の無い行は除外する。
2. `approval_status = CANCEL_APPLIED` の行だけを対象に絞る。
3. `approval_status` を `CANCEL_APPLIED → CANCELLED` へ UPDATE する（実際に遷移した件数を返す）。
4. 現行 felix_total 側の業者選定状態を、承認の段を逆順にたどって外す。
   1. `FelixTotalQuoteRequestGateway::cancelTmpSelection()`（`update_tmp_company_select_flg` / `mode=false`）
      … `estimate_units.tmp_company_id=NULL` / `company_select_status=1` / `estimate_unit_companies.tmp_status=NULL`
   2. `FelixTotalQuoteRequestGateway::cancelAdoption()`（`update_adoption_flg` / `mode=false`）
      … `adoption_flg=0` / `company_select_flg=NULL` / `estimate_units.vendor_id=NULL`・`price` 再計算
5. felix_total が失敗した場合は 3 の UPDATE をロールバックする。

> 取消承認は部長承認済み（建設部選定済み）からの遷移のため、採用だけでなく建設部選定も外す。
> 採用のみ外すと `estimate_units.tmp_company_id` が採用外の業者を指したまま残るためである。

- 承認成功時（件数 > 0）、対象見積先が属する項目（重複排除）のコメントスレッドへ
  `【取消承認】{理由}` を操作者（部長）の発言として自動投稿する。

### 6.4 応答

- 成功: `back()->with('success', "取消承認を実行しました。（n件）")`。
- 0件: `back()->with('error', '取消承認を実行できませんでした。対象の見積先をご確認ください。')`。
- 例外: `ServiceException` → トースト。

理由モーダル UI（`actionModalOpen`）:
- ゴールド系配色。見積先名を明示し「{取消承認}します」と案内。理由未入力・送信中は OK を無効化。

### 6.5 否認（取消の却下・1件ずつ理由必須）

取消を認めない場合は「否認」で却下する。ステータスは**取消前の `APPROVED` のまま据え置く**
（`CANCELLED` にも `DRAFT` にもしない）。処理フロー G列「取消否認 → `APPROVED` に戻す」に対応する。

**フロー**

1. 行の「否認」ボタン → 否認理由モーダル（赤系「否認（取消を却下）」）を開く（対象1件）。
2. 理由を入力し「否認する」→ `RejectPayableRequest`（`partnerId` / `reason`）を POST。
3. `rejectCancelApproval` が `t_payable_partners.approval_status` を
   `CANCEL_APPLIED → APPROVED` へ戻す（`advanceStatus`）。
4. 対象項目のコメントスレッドへ `【否認】{理由}` を部長の発言として自動投稿する（Service）。

**入力**（`RejectPayableRequest`。部長承認の否認と共用）

| 項目 | 必須 | 検証 |
| --- | --- | --- |
| `partnerId` | ○ | `integer` / `exists:t_payable_partners,id` |
| `reason` | ○ | `string` / `max:1000` |

**felix_total 連携は行わない。** 取消申請（`recordCancelRequests`）が新テーブルの状態を進めるだけで
felix_total を呼んでいないため、その却下も新テーブルの状態を戻すだけでよい（現行側は承認済みのまま）。

**応答**

- 成功: `back()->with('success', '否認しました。取消申請を却下し、承認済みのまま据え置きます。')`
- 0件（`CANCEL_APPLIED` 以外）: `back()->with('error', '否認できませんでした。対象の見積先をご確認ください。')`
- 例外: `ServiceException` → トースト

## 7. 共通機能の利用

- **やり取り（コメント）**: 全画面共通。部長（manager）視点で発言（共通仕様 §4）。取消承認理由もここに残る。
- **iframe モーダル**: 「見積先の詳細」（会社名リンク）（共通仕様 §5）。
- **フィルタ**: `keyword` / `itemLabel` / `vendor` / `comment`（`answer` は未使用）（共通仕様 §3）。

## 7.4 画面の表示条件

> 出典: **見積管理_処理フロー**（H列 初期表示条件 / I列 絞り込み条件 / J列 表示承認ステータス /
> K列 ステータス外表示形式 / L列 業者マイページ）。

### 初期表示条件

- 区分が**支払**
- **取消申請されている**

### 絞り込み条件

> 表の見方（処理フロー I列の記法）
> - **単一選択**（`・` 区切り）… セグメント／ラジオ。**初期値**の列が画面初期表示時の選択。
> - **チェックボックス**（`・` 区切りなし）… 単独のトグル。**初期値**が ON のものは初期表示時からチェック済み。

| 項目 | 形式 | 選択肢 | 初期値 |
| --- | --- | --- | --- |
| 区分 | 単一選択 | 全て / 支払 | **支払** |
| コメント | 単一選択 | 全て / コメントあり / コメントなし | **全て** |


> **区分の切り替え**
> - **支払**（初期値）… `t_payable_partners` の取引先だけを表示する。
> - **全て** … 支払に加えて `t_billing_partners`（請求）の取引先も**同じ一覧に並べる**。
>   請求行は承認ステータスに関わらず**表示のみ**で操作できない（サーバが `operable = false` を返す）。
>   また **絞り込みはすべて支払（自区分）の行にのみ適用**し、請求行は絞り込まない。
>   自区分にヒットが無い項目は請求行ごと非表示になる（共通仕様 §3.3）。

### 表示する承認ステータス

| ステータス | 意味 |
| --- | --- |
| `CANCEL_APPLIED` | 取消申請中（取消承認待ち） |

### 表示ステータス以外のデータの扱い

`CANCEL_APPLIED` 以外のステータスのデータは**表示しない**（一覧に出さない）。
※ 他画面は「出すが操作させない」なのに対し、本画面だけ非表示である点に注意。

### 業者マイページ側の操作

なし。

## 7.5 操作 → データ更新先

> 出典: **見積管理_処理フロー**（G列「データ更新先」）。
> 表の「更新先」はスプレッドシートの記述をそのまま構造化したもの。現行実装との差異は下の注記に記す。

| 操作 | 更新先 |
| --- | --- |
| **取消承認** | 支払取引先（`t_payable_partners`）の承認ステータスを更新（`CANCEL_APPLIED` → `CANCELLED`） |
| **取消否認** | 支払取引先（`t_payable_partners`）の承認ステータスを更新<br>コメント（`t_comments`）に登録 |

**現行実装との差異**

- **「取消否認」は未実装**。現在の画面には取消承認のボタンしか無い。
  否認時の差し戻し先ステータス（`CANCEL_APPLIED` → `APPROVED` に戻す想定か）を確定してから実装すること。
- 取消承認では felix_total 側の業者選定状態（建設部選定・採用）も外している（§6.3）。

## 7.6 取消承認・取消否認の遷移先 ★要確認

処理フロー（G列）の記載は次のとおり。

| 操作 | 記載 |
| --- | --- |
| 取消承認 | 支払取引先の承認ステータスを更新 → **`UNSELECTED`：未選定（承認申請なし）** |
| 取消否認 | 支払取引先の承認ステータスを更新 → **`APPROVED`：部長承認済（承認完了）状態にする** ／ コメント(`t_comments`)に登録 |

**取消承認の遷移先 `UNSELECTED` は旧語彙**で、新しい語彙（J列）には存在しない。
一方【支払】見積依頼の「表示する承認ステータス」には `CANCELLED`（取消承認済）が含まれており、
取消後は見積依頼画面へ戻る建て付けになっている。したがって

- **取消承認 → `CANCELLED`**（見積依頼画面に戻る）
- 旧語彙の `UNSELECTED` は `DRAFT` に相当

と読み替えるのが整合するが、**処理フロー側の記載と食い違うため要確認**。

**取消否認 → `APPROVED` に戻す**は明確なので、これで実装済み（§6.5）。

## 8. 留意事項

- 取消承認により `CANCELLED` に到達し、見積先のワークフローは完了扱いとなる（以降どの画面にも現れない）。
- 新スキーマの遷移に続けて felix_total の業者選定状態（建設部選定・採用）を外す（§6.3）。
  現行側は業者選定前の状態に戻るため、実行予算画面から再度の採用操作が可能になる。
