# 【支払】業者選定 詳細設計書

> 共通の仕組み（ヘッダー / フィルタ / やり取り / iframe / テーマ / 送信・エラー方針）は
> [共通仕様_詳細設計.md](./00_共通仕様_詳細設計.md) を参照。本書は本画面固有の差分を記述する。

## 1. 概要

- **画面名**: 【支払】業者選定【業者→FELIX返答済】
- **mode**: `vendor-selection`
- **操作ロール**: 建設部、システム開発、administrator
- **目的**: 業者から相見積の回答が返ってきた見積先の中から、発注する業者を選定（採用）して確定する。
  確定すると担当承認済（`APPLIED`）となり、部長承認へ進む。

業務フロー上の位置づけ:

```
見積依頼 ──▶【業者選定】 ──確定──▶ 部長承認 ──▶ 部長取消申請 ──▶ 部長取消承認
                 ▲
                 └─ 部長承認で否認されると、ここへ差し戻される（DRAFT ＋「【否認】」コメント）
```

## 2. 機能説明

本画面の操作は、**画面上部の「絞り込み・操作バー」のボタン**と、**明細（各行）のボタン**の
2つのボタン群から行う。以下ではボタンごとに実行される処理を分けて記載する。

前提となる一覧表示: 業者から見積回答が返ってきた未選定（`DRAFT`）の見積先を「実行予算 → 項目 →
見積先」の明細で一覧表示する。部長承認で否認され差し戻された見積先（`denied`）もここに現れる。（→ §4, §5）

## 4. 表示データ・抽出条件

- 対象ステータス: `approval_status = DRAFT`（業者未選定）。
- 回答状態フィルタ（`answer`）が使える。回答あり＝最新相見積履歴（`is_latest`）を持つ見積先。
- 相見積額（`quotePrice`）は最新の相見積履歴（`latestHistory.amount_excluding_tax`）を表示する。
- 否認差し戻し分（項目のコメントに「【否認】」の投稿あり）もここに現れる（`denied=true`）。

主な行フィールド:

| フィールド | 内容 |
| --- | --- |
| `selected` | 選定済みか（`approval_status !== DRAFT`） |
| `quotePrice` | 相見積（最新履歴の税抜額）。回答なしは選定不可 |
| `provisional` | 仮選定（`is_drafted === 1`）。ボタンを緑表示にする |
| `denied` | 否認差し戻し（項目のコメントに「【否認】」の投稿あり）。ボタンを赤表示にする |

## 6. 固有の操作仕様（toggle-button）

業者選定は他画面と異なり「サーバの選定状態を初期値に、押下でトグルする」方式（選び替え）。

### 6.1 選定トグル（`toggleSelect`）

- 選定可能なのは**見積回答あり**（`quotePrice != null && quotePrice > 0`）の行のみ。回答なしは
  ボタンを無効化（`見積回答が無いため選定できません`）。
- サーバ状態（`serverSelected` = `row.selected`）を初期値に、ローカル `selectionOverride` で上書き。
- `vendorDirty`（サーバ状態から1つでも押下変更があるか）かつ選定1件以上でヘッダー確定を活性化。
- **一括選択（全て選定）は用意しない。** 業者選定は案件ごとに 1 業者を選ぶ画面のため、
  ヘッダーの一括選択ボタン自体を表示しない（行ごとのトグルのみ）。

### 6.2 ボタンの状態色（共通仕様 §6 参照）

- 赤: 否認差し戻し（`denied`）で、同一項目のどの業者もまだ選定されていない。
- 緑: 仮選定済み、または否認差し戻しが同一項目のいずれかの選定で解消された（赤→緑）。
- ゴールド: 通常。

### 6.3 仮選定の保存（`provisional`）

チェック相当の操作で `t_payable_partners.is_drafted` を即時保存する（見積依頼画面と同じ API）。
本画面では選定トグルの状態色（緑）判定に用いる。

## 7. 確定処理（発注業者を確定）

### 7.1 入力・フロー

1. 回答ありの見積先を選定 → ヘッダー「発注業者を確定（n）」が活性化。
2. 確定 → `ConfirmVendorSelectionRequest` へ `partnerIds` を POST。
3. `VendorSelectionService::confirm()` → `PayableRepository::recordVendorSelections()`。

バリデーション（`ConfirmVendorSelectionRequest`）:
- `partnerIds`: required / array / min:1
- `partnerIds.*`: integer / distinct / `exists:t_payable_partners,id`

### 7.2 felix_total 連携（`recordVendorSelections`）

- 見積先を旧 ID（`unit` = 項目 `source_id` / `company` = 見積先 `source_id`）へ写像する。
処理順は **「新テーブルを更新 → 現行 felix_total の API を呼ぶ」** で、1トランザクションにまとめる
（`syncWithFelixTotal()`）。

1. 見積先を旧 ID（`unit` = 項目 `source_id` / `company` = 見積先 `source_id`）へ写像する。
   移行元（`source_id`）の無い行は除外する。
2. `approval_status = DRAFT` の行だけを対象に絞る（二重送信・状態不整合の防止）。
3. 新スキーマの `approval_status` を `DRAFT → APPLIED` へ UPDATE する。
4. 対象行につき felix_total の採用処理 `FelixTotalQuoteRequestGateway::adoptCompany($unit, $company)`
   を呼ぶ（`update_adoption_flg` を `mode='true'` で実行）。
5. felix_total が失敗（接続不可・非 2xx）した場合は例外が送出され、**3 の UPDATE はロールバック**される
   （両方書けたときだけ成功として扱う）。

戻り値は 3 で実際に遷移した件数。

### 7.3 応答

- 成功: `back()->with('success', "発注業者を確定しました。（n件）")`。
- 0件: `back()->with('error', '発注業者を確定できませんでした。選定した見積先をご確認ください。')`。
- 例外: `ServiceException` → トースト。

## 8. 共通機能の利用

- **やり取り（コメント）**: 全画面共通。担当（staff）視点で発言（共通仕様 §4）。部長承認画面の部長と
  同じ項目スレッドを共有する。否認・取消の理由コメントもここに現れる。
- **iframe モーダル**: 「見積先の詳細」（会社名リンク）（共通仕様 §5）。
- **フィルタ**: `keyword` / `itemLabel` / `vendor` / `answer` / `comment`（共通仕様 §3）。

## 8.5 もらい（請求）行の扱い ★ もらい運用フロー ⑦

もらい（請求先）の行は本画面に**表示のみ**で現れる（出典:
[`docs/operations/もらい_運用フロー.drawio`](../../operations/もらい_運用フロー.drawio) ⑦）。

- もらいは業者との金額すり合わせが TEL で完了しているため **選定不要**。業者選定列のボタンは**非活性**にする。
- **標準単価 / 予算単価 / 仮選定**列は「—」表示。
- 見積額列には【請求】見積作成（③）で入力した金額を表示する。
- **「請求先にする」は本画面では変更できない**（区分の変更は業者追加画面で行う）。

請求側の一連の画面は [06_請求_見積作成](./06_請求_見積作成_詳細設計.md)〜
[09_請求_見積取消承認](./09_請求_見積取消承認_詳細設計.md) を参照。

## 8.55 画面の表示条件

> 出典: **見積管理_処理フロー**（H列 初期表示条件 / I列 絞り込み条件 / J列 表示承認ステータス /
> K列 ステータス外表示形式 / L列 業者マイページ）。

### 初期表示条件

- 区分が**支払**
- **選定が1つも設定されていない**

### 絞り込み条件

> 表の見方（処理フロー I列の記法）
> - **単一選択**（`・` 区切り）… セグメント／ラジオ。**初期値**の列が画面初期表示時の選択。
> - **チェックボックス**（`・` 区切りなし）… 単独のトグル。**初期値**が ON のものは初期表示時からチェック済み。

| 項目 | 形式 | 選択肢 | 初期値 |
| --- | --- | --- | --- |
| 区分 | 単一選択 | 全て / 支払 | **支払** |
| 回答状態 | 単一選択 | 全て / 見積回答あり / 見積回答なし | **全て** |
| 仮選定のみ表示 | チェックボックス | — | OFF |
| 業者未選定 | チェックボックス | — | **ON** |
| コメント | 単一選択 | 全て / コメントあり / コメントなし | **全て** |

> **「業者未選定」チェックボックス**（`operableFilterLabel`）
> - 初期表示は **ON**。まだ業者を選定していない行（`operable` ＝承認ステータス `DRAFT`）だけを表示し、
>   担当者が着手すべき行から始められるようにする。
> - チェックを外すと**全件表示**（選定済み・承認済みなど他ステータスの行も並ぶ。操作は不可）。


> **区分の切り替え**
> - **支払**（初期値）… `t_payable_partners` の取引先だけを表示する。
> - **全て** … 支払に加えて `t_billing_partners`（請求）の取引先も**同じ一覧に並べる**。
>   請求行は承認ステータスに関わらず**表示のみ**で操作できない（サーバが `operable = false` を返す）。
>   また **絞り込みはすべて支払（自区分）の行にのみ適用**し、請求行は絞り込まない。
>   自区分にヒットが無い項目は請求行ごと非表示になる（共通仕様 §3.3）。

### 表示する承認ステータス

| ステータス | 意味 | 追加条件 |
| --- | --- | --- |
| `DRAFT` | 未申請 | **業者側から見積回答されていること**（`t_payable_quotations` にデータがある） |

### 表示ステータス以外のデータの扱い

**同一項目に複数の見積先がある場合、進んでいるパートナーだけを操作不可にし、他のパートナーは選定できる。**

| ステータス | 挙動 |
| --- | --- |
| `APPLIED`（申請中＝部長承認待ち） | そのパートナーは選定できない。**他パートナーは選定可能** |
| `APPROVED`（承認済） | そのパートナーは選定できない。**他パートナーは選定可能** |
| `CANCEL_APPLIED`（取消申請中） | 部長承認済みのパートナーは選定できない。**他パートナーは選定可能** |

> これは **1項目に複数の業者を選定できる**ことを前提にした仕様である
> （現行 felix_total も原価項目の `no_competitive_flg = 1`（相見積しない）なら複数採用可。→ §9）。

### 選定の前提条件

**支払見積（`t_payable_quotations`）にデータが存在する場合に選定できる**（＝業者から見積回答があること）。

### 業者マイページ側の操作

なし。

## 8.6 操作 → データ更新先

> 出典: **見積管理_処理フロー**（G列「データ更新先」）。
> 表の「更新先」はスプレッドシートの記述をそのまま構造化したもの。現行実装との差異は下の注記に記す。

| 操作 | 更新先 |
| --- | --- |
| **選定**（発注業者を確定） | 支払取引先（`t_payable_partners`）の承認ステータスを更新（`DRAFT` → `APPLIED`）<br>選定された業者が「部長承認」画面に表示される |

**現行実装との差異**

- 承認ステータスの更新に加え、felix_total の採用（`update_adoption_flg`）をサーバ間 HTTP で呼ぶ（§7.2）。

## 9. 留意事項

- **1項目に複数の業者を選定できる**（処理フロー K列「他パートナーは選定可能」）。
  現行 felix_total も原価項目マスタの `no_competitive_flg = 1`（相見積しない）なら複数採用でき、
  実データでも 50,528 項目中 1,669 項目が複数採用になっている。
  **ただし現在の実装は `no_competitive_flg` を常に 0 で渡している**ため、
  相見積しない項目を新Fixから選定すると既存の採用が外れて1社だけになる。
  一覧取得時に項目の値（`cost_units.no_competitive_flg` → `estimate_units.no_competitive_unit_flg`
  の順に解決）を引いて `adoptCompany()` へ渡すよう直すこと。
- 選定できるのは **`t_payable_quotations` にデータが存在する見積先**（＝業者から見積回答があるもの）。
- 送信成功後はリロードされるため、ローカルの選定上書き（`selectionOverride`）はクリアする。
