# 【支払】部長取消申請 詳細設計書

> 共通の仕組み（ヘッダー / フィルタ / やり取り / iframe / テーマ / 送信・エラー方針）は
> [共通仕様_詳細設計.md](./00_共通仕様_詳細設計.md) を参照。本書は本画面固有の差分を記述する。

## 1. 概要

- **画面名**: 【支払】部長取消申請【FELIX(担当者)→FELIX(建設部部長)】
- **mode**: `cancel-request`
- **操作ロール**: 建設部、システム開発、administrator
- **目的**: 部長承認済（`APPROVED`）の見積先について、選定の取消を**申請**する。
  申請すると取消申請中（`CANCEL_APPLIED`）となり、部長取消承認へ進む。理由の入力を必須とする。

業務フロー上の位置づけ:

```
部長承認 ──▶【部長取消申請】──申請──▶ 部長取消承認 ──▶（CANCELLED＝完了）
```

## 2. 機能説明

本画面の操作は、**画面上部の「絞り込み・操作バー」のボタン**と、**明細（各行）のボタン**の
2つのボタン群から行う。以下ではボタンごとに実行される処理を分けて記載する。

前提となる一覧表示: 部長承認済（`APPROVED`）の見積先を「実行予算 → 項目 → 見積先」の明細で
一覧表示する。見積額は確定見積を表示する。本画面は**1レコードごとに理由入力モーダルで単体実行**する
方式のため、ヘッダーの一括アクションボタン・「全て選択」は出さない。（→ §4, §5）

### 2.1 絞り込み・操作バーのボタン（画面上部）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 絞り込み（検索） | 実行予算名 / 項目名 / 見積先名でサーバ側フィルタし、一覧を再取得する。 | 共通仕様 §3 |
| コメント有無フィルタ | 全て / コメントあり / コメントなしでサーバ側フィルタする。 | 共通仕様 §3 |
| 明細を全て開く / 閉じる | 全実行予算カードの明細を一括で開閉する。 | §5 |

> 本画面は per-row 方式（`isPerRowAction`）のため、「全て選択」「一括アクション」ボタン、
> および「回答状態フィルタ」は表示しない。

**検索項目（絞り込み検索フォーム）**: 下記3項目を入力し「絞り込み検索」ボタンで送信すると、
条件に一致する一覧をサーバから再取得する。いずれも**部分一致（LIKE）**で、空欄の項目は条件から除外する。

| 入力欄（画面ラベル） | 検索対象 | 条件 |
| --- | --- | --- |
| 物件名 | 実行予算名（`t_buildings.building_name`） | 部分一致 |
| 項目名 | 費用項目名（`t_building_budget_items.item_name`） | 部分一致 |
| 見積先 | 見積先の会社名（`company_name`） | 部分一致 |

### 2.2 明細のボタン（各行）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 取消申請 | 押下で理由入力モーダルを開き、理由を入力して1件ずつ取消を申請する（`CANCEL_APPLIED` へ）。 | §6 |
| やり取り（吹き出し） | 項目単位のコメントスレッドを開き、建設部メンバー⇔部長でやり取りする。未読バッヂ・添付に対応。 | 共通仕様 §4 |
| 見積先の詳細（会社名リンク） | felix_total の見積先編集画面を iframe モーダルで開く。 | 共通仕様 §5 |

## 3. ルーティング / レイヤ

| 種別 | ルート名 | メソッド | 実装 |
| --- | --- | --- | --- |
| 一覧 | `quotation-management.cancel-request` | GET | `CancelRequestController::index` |
| 申請 | `quotation-management.cancel-request.confirm` | POST | `CancelRequestController::confirm` |

- ページ: `resources/js/pages/quotation/payable/cancel-request/ui/CancelRequestPage.vue`。
- Service: `CancelRequestService`（`paginate` / `confirm`。`CommentService` を DI）。
- Repository: `PayableRepository`（`recordCancelRequests` = `advanceStatus(APPROVED → CANCEL_APPLIED)` / `itemIdForQuotation`）。

## 4. 表示データ・抽出条件

- 対象ステータス: `approval_status = APPROVED`（部長承認済）。
- 見積額列は**確定見積**（`quoteColumnLabel = '確定見積'`）＝選定済みの見積先の最新見積の
  `subtotal_amount`（→ [共通仕様](./00_共通仕様_詳細設計.md) §1.2.1）。
- 回答状態フィルタ（`answer`）は使わない。

主な行フィールド:

| フィールド | 内容 |
| --- | --- |
| `cancelRequested` | 取消申請中か（`approval_status === CANCEL_APPLIED`） |
| `quotePrice` | 確定見積（選定済み見積先の `subtotal_amount`） |

## 5. 画面レイアウト（明細テーブルの列）

| 列 | 内容 |
| --- | --- |
| 項目 | 項目名（表示中の先頭行のみ）＋ やり取り吹き出し |
| 見積先 | 会社名（iframeで詳細表示） |
| 標準単価(税抜) | `masterPrice` |
| 予算単価(税抜) | `budgetPrice` |
| 確定見積(税抜) | `quotePrice` |
| 取消申請 | 行アクションボタン（`kind=pick-button` ＋ 1件ずつ理由モーダル。押下=`取消申請`） |

- 本画面は**1レコードごとに理由入力モーダル → OK で単体実行**する方式（`isPerRowAction=true`）。
  そのため、ヘッダーの一括アクションボタン・「全て選択」は**出さない**。

## 6. 操作仕様（取消申請・1件ずつ理由必須）

### 6.1 フロー

1. 行の「取消申請」ボタン → 理由入力モーダルを開く（対象1件・`partnerIds=[partnerId]`）。
2. 理由を入力し OK → `CancelActionRequest` を POST。
3. `CancelRequestService::confirm($partnerIds, $reason)`。

### 6.2 入力（`CancelActionRequest`）

- `partnerIds`: required / array / min:1
- `partnerIds.*`: integer / distinct / `exists:t_payable_partners,id`
- `reason`: required / string / max:1000（**理由は必須**）

### 6.3 処理（`recordCancelRequests`）

- `advanceStatus`: `approval_status` が `APPROVED` の行のみ `CANCEL_APPLIED` へ UPDATE
  （実際に `APPROVED` だった件数を返す）。
- 申請成功時（件数 > 0）、対象見積先が属する項目（重複排除）のコメントスレッドへ
  `【取消申請】{理由}` を操作者の発言として自動投稿する。

### 6.4 応答

- 成功: `back()->with('success', "取消申請を実行しました。（n件）")`。
- 0件: `back()->with('error', '取消申請を実行できませんでした。対象の見積先をご確認ください。')`。
- 例外: `ServiceException` → トースト。

理由モーダル UI（`actionModalOpen`）:
- ゴールド系配色。見積先名を明示し「{取消申請}します」と案内。
- 理由未入力・送信中は OK を無効化。

## 7. 共通機能の利用

- **やり取り（コメント）**: 全画面共通。担当（staff）視点で発言（共通仕様 §4）。取消申請理由もここに残る。
- **iframe モーダル**: 「見積先の詳細」（会社名リンク）（共通仕様 §5）。
- **フィルタ**: `keyword` / `itemLabel` / `vendor` / `comment`（`answer` は未使用）（共通仕様 §3）。

## 7.4 画面の表示条件

> 出典: **見積管理_処理フロー**（H列 初期表示条件 / I列 絞り込み条件 / J列 表示承認ステータス /
> K列 ステータス外表示形式 / L列 業者マイページ）。

### 初期表示条件

- 区分が**支払**
- **選定済み**

### 絞り込み条件

> 表の見方（処理フロー I列の記法）
> - **単一選択**（`・` 区切り）… セグメント／ラジオ。**初期値**の列が画面初期表示時の選択。
> - **チェックボックス**（`・` 区切りなし）… 単独のトグル。**初期値**が ON のものは初期表示時からチェック済み。

| 項目 | 形式 | 選択肢 | 初期値 |
| --- | --- | --- | --- |
| 区分 | 単一選択 | 全て / 支払 | **支払** |
| 申請可能 | チェックボックス | — | **ON** |
| コメント | 単一選択 | 全て / コメントあり / コメントなし | **全て** |

> **「申請可能」チェックボックス**（`operableFilterLabel`）
> - 初期表示は **ON**。取消申請できる行（`operable` ＝承認ステータス `APPROVED`）だけを表示する。
> - チェックを外すと**全件表示**（申請済み・取消済みなど他ステータスの行も並ぶ。操作は不可）。


> **区分の切り替え**
> - **支払**（初期値）… `t_payable_partners` の取引先だけを表示する。
> - **全て** … 支払に加えて `t_billing_partners`（請求）の取引先も**同じ一覧に並べる**。
>   請求行は承認ステータスに関わらず**表示のみ**で操作できない（サーバが `operable = false` を返す）。
>   また **絞り込みはすべて支払（自区分）の行にのみ適用**し、請求行は絞り込まない。
>   自区分にヒットが無い項目は請求行ごと非表示になる（共通仕様 §3.3）。

### 表示する承認ステータス

| ステータス | 意味 |
| --- | --- |
| `APPROVED` | 承認済（承認完了） |

### 表示ステータス以外のデータの扱い

`APPROVED` 以外のステータスのデータは**取消申請できない**。

### 業者マイページ側の操作

なし。

## 7.5 操作 → データ更新先

> 出典: **見積管理_処理フロー**（G列「データ更新先」）。
> 表の「更新先」はスプレッドシートの記述をそのまま構造化したもの。現行実装との差異は下の注記に記す。

| 操作 | 更新先 |
| --- | --- |
| **取消申請** | 支払取引先（`t_payable_partners`）の承認ステータスを更新（`APPROVED` → `CANCEL_APPLIED`） |

**現行実装との差異**

- 申請理由は項目のコメント（`t_comments`）へ `【取消申請】{理由}` として投稿している（処理フローの表には記載が無いが、実装済み）。

## 8. 留意事項

- 取消系はステータスを新スキーマの直接 UPDATE で進める（felix_total 連携は伴わない）。
- 申請したものは部長取消承認画面（`CANCEL_APPLIED`）に現れ、部長が承認すると完了（`CANCELLED`）となる。
