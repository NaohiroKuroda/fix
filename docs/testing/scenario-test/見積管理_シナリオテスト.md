## 0. 実行予算作成（前提データの準備｜felix_total 側）

> 見積管理（fix）は **felix_total（現行）の実行予算** を参照する画面群であり、テストデータは
> **felix_total 側で実行予算を作成** して用意する。本シナリオは **この実行予算作成を起点** とする。
> fix と felix_total は **同一 MySQL（`fix`）を共有** し、felix_total の保存契機で新見積テーブルへ同期される。

### 同期の仕組み（felix_total → fix 新テーブル）

felix_total の `NewQuotationRegisterService` が、実行予算の保存契機で fix 参照テーブルへ登録（同期）する。
`source_id` に移行元 ID を保持し、突合キーとして使う（`approval_status` / `is_drafted` は fix 独自項目のため
同期側は触らず、DB 既定値＝初期 `UNSELECTED` に委ねる）。

| felix_total（旧） | fix（新・参照先） | `source_id` に入る値 | 同期契機（コード） |
| :-- | :-- | :-- | :-- |
| `estimates` | `t_buildings`（案件＝実行予算） | `estimates.id` | 実行予算フォーム保存（`EstimateController` → `register(id, wasRecentlyCreated)`） |
| `estimate_units`（`step=2`/`sub_cate=2` の建設費用項目） | `t_building_budget_items`（費用項目） | `estimate_units.id` | 上記 `register` ＋ 項目追加（`AddEstimateUnitController` → `registerAddCostItemWithRelations`） |
| `estimate_unit_companies`（見積先＝業者） | `t_payable_partners`（費用見積） | `estimate_unit_companies.id` | 上記 `register`（初期 `approval_status=UNSELECTED`） |
| 相見積回答（`estimate_unit_company_files` type=1／明細） | `t_payable_quotations` / `t_payable_quotation_details` | `file.id` / `cost_unit_estimate_units.id` | 業者マイページ保存（`Http\EstimateController@save` → `NewCostQuotationHistoryRegisterService::register`） |
| 見積依頼送信（`estimate_order_histories`） | `t_payable_quotation_requests`（費用見積依頼） | `estimate_order_histories.id` | 見積依頼送信（`EstimateCustomDetailController::order_estimate` → `NewCostQuotationRequestRegisterService::register`） |
| グループ設計ファイル充足（`check_file_storage`） | `t_building_group_statuses.is_completed` | — | バッチ（`CheckNoEstimate` → `NewBuildingGroupStatusRegisterService::syncByEstimate`） |

> felix_total 側の登録処理の全体像・契機・対象テーブル・テストケースは **§16** に集約する。上表はその要約。

### 手順（felix_total `/admin`）

1. **実行予算を作成・保存**する（`estimates`）。→ `t_buildings` に `source_id=estimates.id` で1案件が登録される。
2. **建設費用項目を追加**する（`estimate_units`、`step=2`/`sub_cate=2`）。→ `t_building_budget_items` に `source_id=estimate_units.id` で同期。
3. **各項目に見積先（業者）を追加**する（`estimate_unit_companies`）。→ `t_payable_partners` に `source_id=estimate_unit_companies.id`・`approval_status=UNSELECTED` で同期。
4. （業者選定テスト用）**業者マイページ（`estimate/edit`）で相見積回答額を保存**する。→ 相見積履歴（S5）が同期され、業者選定画面で「回答あり」になる。

### 期待結果

- **ST-BUDGET-01**: 実行予算を保存すると、fix 見積依頼画面に該当実行予算カード（物件名＝`building_name`）＋項目＋見積先が **`source_id` 付き** で表示される。
- **ST-BUDGET-02**: 追加した見積先の初期状態は `approval_status=UNSELECTED`（＝見積依頼・業者選定の対象）。
- **ST-BUDGET-03**: 相見積回答を入れた見積先のみ、業者選定画面で「選定する」が活性になる（回答無しは選定不可＝ST-VS-01）。
- **ST-BUDGET-E01**: 移行元（`source_id`）が同期されない見積先は fix 見積管理に **表示されない／依頼対象外**（`source_id` 非 NULL が前提）。
- **ST-BUDGET-E02**: felix_total 側の同期（`NewQuotationRegisterService`）が例外で失敗した場合、fix 参照テーブルに反映されず一覧に出ない（felix_total 側ログを確認）。

> 以降の §1〜§15 は、この §0 で用意した実行予算（案件・項目・見積先）に対する fix 見積管理の操作・期待を定義する。

## 2. 見積依頼画面（担当）

前提: Fix で実行予算を作成した時点で対象業者に見積依頼行が存在（`source_id` あり、承認状態非依存）。

操作:
1. `engineer_test` で見積依頼画面を開く。
2. 未依頼の見積先をチェックし、ヘッダーの「全て依頼／依頼を解除」または個別チェックで選択。
3. 「見積依頼を送信」を実行。
4. 仮選定トグル（`is_drafted`）を切り替える。

- **ST-QR-01**: 未依頼行のみ初期表示（「未依頼のみ表示」フィルタが `quote-request` で初期ON）。
- **ST-QR-02**: 送信すると成功トースト「見積依頼を送信しました。（n件）」が出て、行が依頼済みになる。
- **ST-QR-03**: 0件送信時は「見積依頼を送信できませんでした。…」が出る。
- **ST-QR-04**: 仮選定トグルが即時保存され（`preserveScroll`）、失敗時はロールバックする。
- **ST-QR-05**: 依頼済み行も `reselectable` によりチェック可能（再依頼）。
- **ST-QR-06**: 会社名リンク・業者追加・業者マイページの各 iframe/別タブが開く（URL 未設定時はプレーン表示）。

## 3. 業者選定画面（担当）

前提: 見積依頼済み・未選定（`approval_status = UNSELECTED`）の見積先。

操作:
1. 業者選定画面を開く。
2. 見積回答（相見積額）がある行の「選定する」を押下（トグル）。
3. ヘッダーの「確定」で送信。

- **ST-VS-01**: 見積回答が無い行は選定不可（「見積回答が無いため選定できません」）。
- **ST-VS-02**: 選定トグルはサーバ状態を初期値に、押下で切り替わる（選び替え）。
- **ST-VS-03**: 「確定」は変更があり選定1件以上のとき活性（`vendorDirty && size>0`）。
- **ST-VS-04**: 確定で「発注業者を確定しました。（n件）」トースト。
- **ST-VS-05**: 否認差し戻し行はボタンが赤（未選定）／同項目のいずれかが選定されると緑へ。
- **ST-VS-06**: 回答状態フィルタ（全て / 回答あり / 回答なし）で絞り込める。
- **ST-VS-07**: 一括選択（「全て選定」）ボタンは表示されない（行ごとのトグルのみ）。
- **ST-VS-08**: 「業者未選定」チェックボックスが **初期表示で ON**。未選定（`DRAFT`）の行だけが並ぶ。
- **ST-VS-09**: 「業者未選定」のチェックを外すと **全ステータスの行が並ぶ**（選定済み・承認済み等。操作は不可）。

## 8. 添付ファイル
### 8-1. 上限・件数
- **ST-FILE-01**: 1送信あたり **最大5件**まで添付できる。6件目以降はフロントで弾かれ「添付は5件までです。」表示（サーバ側も `max:5`）。
- **ST-FILE-02**: 1ファイル **最大10MB**。超過はフロントで「(ファイル名)（10MB超）」を表示して弾く（サーバ側 `max:10240`）。
- **ST-FILE-03（環境）**: 10MB前後のファイルが送信成功するには `upload_max_filesize`≥12M / `post_max_size`≥64M が必要（§0の環境設定）。設定不足だと 422「送信に失敗しました」になる。

### 8-2. 許可拡張子
- **ST-FILE-04**: 許可拡張子（画像 jpg/jpeg/png/gif/webp/heic/heif、文書 pdf/txt、Office xlsx/xls/docx/doc/pptx/ppt/csv、CAD dwg/dxf/jww/jwc/sfc/p21、圧縮 zip）が送信できる。
- **ST-FILE-05**: `svg` / `exe` / `php` / `html` 等ホワイトリスト外は、フロント（`accept`＋事前チェック）とサーバ（`extensions`）の両方で拒否される。
- **ST-FILE-06（拡張子偽装）**: 中身がテキスト等の非画像なのに `.jpg` 拡張子を付けたファイルは、保存時の実体検証（`getimagesize`）で拒否される。

### 8-3. 画像圧縮・サムネイル
- **ST-FILE-07**: 長辺1920pxを超える画像は、送信時に **長辺1920へ縮小**して保存される（1920以下は拡大しない）。
- **ST-FILE-08**: 画像は **長辺400pxのサムネイル（JPEG）** が生成され、チャット吹き出しに **サムネ表示**される。
- **ST-FILE-09**: サムネ／本体をクリックすると **元ファイル（圧縮済み）がダウンロード**される（インライン表示はしない）。
- **ST-FILE-10**: 総ピクセルが約40MP超の画像は、圧縮・サムネをスキップして元を保存（サムネ無し→アイコン表示）。
- **ST-FILE-11**: `heic/heif`・PDF・Office・CAD・zip はサムネを生成せず、**種別アイコン＋ファイル名＋サイズ**で表示。クリックでダウンロード。

### 8-4. 保存・配信
- **ST-FILE-12**: 保存名はUUID化され、本体 `comments/{itemId}/{uuid}.{ext}`、サムネ `comments/{itemId}/thumbs/{uuid}.jpg` の規約パスに保存される。
- **ST-FILE-13**: `t_attachments` にメタ（`file_path` / `original_name` / `mime_type` / `size` / `user_id`）が記録される。
- **ST-FILE-14**: サムネ配信は `comment-attachments.thumb`（画像サムネのインライン、`image/jpeg` 固定）、ダウンロードは `comment-attachments.download`（元ファイル名）。いずれも `auth:admin` 必須。

## 9. E2E 通しシナリオ

### ST-E2E-01（正常フロー：依頼→選定→承認）
1. `engineer_test`: 見積依頼で送信 → 業者選定へ。
2. `engineer_test`: 業者選定で回答のある業者を選定 → 確定。
3. `manager_test`: 部長承認で内容確認し「承認」。
- 期待: 状態が `STAFF_APPROVED` → `MANAGER_APPROVED` と進み、承認ではコメントが自動登録されない（ST-MA-02）。

### ST-E2E-02（否認→再選定）
1. `manager_test`: 部長承認で「否認」＋理由。
2. `engineer_test`: 業者選定で否認理由をスレッドで確認（`【否認】…`）し、別業者を選定 → 確定。
- 期待: 否認理由が同一項目スレッドに残り、担当画面から参照できる（ST-MA-04 / ST-CHAT-09）。

### ST-E2E-03（取消：申請→承認）
1. `engineer_test`: 部長取消申請で承認済みデータの取消を申請（＋理由）。
2. `manager_test`: 部長取消承認で承認（＋理由）。
- 期待: `MANAGER_APPROVED` → `CANCEL_REQUESTED` → `APPROVED`、`【取消申請】` `【取消承認】` が時系列でスレッドに残る。

### ST-E2E-04（添付の横断参照）

- **ST-LINK-E03**: felix_total と別親ドメインで cross_auth クッキーが送れない → iframe が「権限がありません」等になる（同一親ドメインが前提）。

### 13-4. 業者追加・項目追加時の同期挙動（★重要 / 実装準拠）

fix 見積管理は felix_total の新テーブル（`t_building_budget_items` / `t_payable_partners`）を参照する。
felix_total 側で **項目（`estimate_units`）や見積先（`estimate_unit_companies`）を追加** しても、
**同期契機（`NewQuotationRegisterService`）が走った操作だけ** が fix に反映される。追加の入口ごとに
同期の有無が異なるため、下表を正とする（§0 の同期表も参照）。

| 追加操作 | 入口 | 同期契機（コード） | fix への反映 |
| :-- | :-- | :-- | :-- |
| **項目を追加** | felix_total 実行予算編集の工程追加（`add-estimate-units` → quick-store） | `AddEstimateUnitController` → `registerAddCostItemWithRelations($estimateUnitId)` | **即時**（項目＋その見積先まで `t_building_budget_items` / `t_payable_partners` へ INSERT） |
| **見積先（業者）を追加** | 見積依頼画面「業者追加」iframe（`estimate-unit-companies/create`） | `EstimateUnitCompanyController` は **同期を呼ばない** | **即時では反映されない**（下記 ST-SYNC-02） |
| 実行予算を保存（既存の再保存含む） | felix_total 実行予算フォーム保存（`EstimateController`） | `register($id, wasRecentlyCreated=false)` → `update()` で **未登録ぶんを INSERT 補完** | 上記で漏れた見積先もここで反映 |

#### 正常系
- **ST-SYNC-01（項目追加）**: felix_total 実行予算に建設費用項目（`step=2`/`sub_cate=2`）を追加 → `registerAddCostItemWithRelations` が発火し、`t_building_budget_items` と紐づく見積先（`t_payable_partners`, 初期 `UNSELECTED`）が作成される → fix 見積管理を再取得すると新項目・新見積先が表示される。
- **ST-SYNC-03（見積先の遅延反映）**: iframe で見積先を追加後、**実行予算を保存し直す**（felix_total フォーム保存）と `register(update)` の `updateCostQuotation`（未登録は INSERT）で `t_payable_partners` に追加され、fix に反映される。
- **ST-SYNC-05**: 追加された見積先の初期状態は `approval_status=UNSELECTED`（見積依頼・業者選定の対象）で、`source_id`（= `estimate_unit_companies.id`）が入る。

#### 異常系・既知の制限
- **ST-SYNC-02（見積先の即時未反映｜★要注意）**: 見積依頼画面「業者追加」iframe（`estimate-unit-companies/create`）で見積先を追加して閉じても、`EstimateUnitCompanyController` に新テーブルへの同期呼び出しが無いため、**閉じた直後の `router.reload` では追加見積先が fix 一覧に出ない**。反映には実行予算の再保存（ST-SYNC-03）が必要。
  - > **§13 ST-LINK-02 との差異**: ST-LINK-02 は「iframe で業者を追加して閉じる → 再取得で反映される」と記すが、**現状の実装では見積先単体の追加に同期契機が無く、即時反映は保証されない**。詳細設計（`docs/detailed-design/quotations/`）で意図する挙動を確認し、即時反映が要件なら `EstimateUnitCompanyController` の保存後フックに同期処理（例: 該当 `estimate_id` に対する `register(update)`）を追加すること。
- **ST-SYNC-04（対象外の項目追加）**: `step=2`/`sub_cate=2` 以外（建設費用項目でない）を追加しても `registerAddCostItemWithRelations` の対象外で `t_building_budget_items` へ同期されず、fix 見積管理には出ない。
- **ST-SYNC-06（建物未同期）**: 対象実行予算が `t_buildings` に未同期（`source_id` 突合先が無い）だと、項目追加同期は建物不在で中断され、fix に出ない（先に実行予算保存で建物を同期しておくこと＝§0）。

## 14. ログ出力

各 Service は各ユースケースを try/catch で囲み、例外時に `Log::error()` で記録してから `ServiceException` を投げる
（`bootstrap/app.php` が画面右上トースト `flash.error` に変換）。**内部情報は画面に出さず、ログにのみ残す**方針。

- 出力先: `storage/logs/laravel.log`（Docker はコンテナ内。確認は `docker exec new_fix_dev tail -f storage/logs/laravel.log`）。
- 記録内容: `message`（例外メッセージ）/ 操作対象（`companyIds` / `filters` / `itemId` 等）/ `file` / `line` / `trace`。

### テストケース
- **ST-LOG-01**: Service 層で例外が発生した際、`Log::error` に **message・対象ID・file・line・trace** が記録される。
- **ST-LOG-02**: 記録される対象キーが処理ごとに適切（見積依頼/選定=一覧は `filters`・更新は `companyIds`、否認=`companyId`、コメント投稿=`itemId`・`fileCount`）。
- **ST-LOG-03**: 例外は `ServiceException` に包まれ、画面には **汎用トーストのみ**（スタックトレース等の内部情報は画面に出ない）。
- **ST-LOG-04**: 入力バリデーションエラー（422）は **`Log::error` されない**（想定内のユーザー入力エラーのため）。0件時の「実行できませんでした」も想定内で、例外ログにはならない。
- **ST-LOG-05**: 添付付きコメントの投稿失敗（偽装拒否・圧縮失敗等）は `QuotationCommentService::post` の catch で `itemId`・`fileCount` 付きで記録される。
- **ST-LOG-06**: felix_total 連携失敗（例: `felix_total へ接続できませんでした。`）が `userId` 付きで記録され、画面はトースト表示になる。

> データを参照** する。ここでは felix_total 側に実装された **登録処理の全体像・契機・対象テーブル・冪等性・失敗時挙動** を

### 16-0. 登録サービス一覧（実装）

| `NewCostQuotationRequestRegisterService::register($eucId)` | 見積依頼送信（`EstimateCustomDetailController::order_estimate`。バッチ `auto_notice_send_mail` ／手動依頼の双方） | `estimate_order_histories` → `t_payable_quotation_requests`（費用見積依頼） | `estimate_order_histories.id` | **サービス内 TX**。例外は **握りつぶしログのみ**（業務保存を妨げない） |
| `NewCostQuotationHistoryRegisterService::register($eucId)` | 業者マイページ保存（`Http\EstimateController::save`） | `estimate_unit_company_files`(type=1) → `t_payable_quotations` / `cost_unit_estimate_units` → `t_payable_quotation_details` | `file.id` / `cost_unit_estimate_units.id` | **サービス内 TX**。例外は **握りつぶしログのみ**。`is_latest` を再計算 |
| `NewBuildingGroupStatusRegisterService::syncByEstimate($estimateId)` | 設計ファイル充足チェックバッチ（`Console\Commands\CheckNoEstimate`） | `Estimate::check_file_storage(group)` → `t_building_group_statuses.is_completed` | —（`building_id`＋`group_code` で突合） | UPDATE のみ（レコードは実行予算作成時に作成済み前提） |

> **fix 独自項目の不可侵**: `t_payable_partners.approval_status` / `is_drafted` は **fix 側の状態管理項目**。同期側（insert/update とも）は
> これらを **一切設定しない**（DB 既定値＝初期 `UNSELECTED` に委ね、既存値を温存する）。→ 実行予算を再保存しても fix の承認状態は戻らない。

### 16-1. 実行予算保存 → 登録（`register`）

- **ST-REG-01（新規＝insert）**: 実行予算を **新規作成** 保存すると（`wasRecentlyCreated=true`）、`insert()` が走り、`t_buildings` 1件＋
  対象項目（step=2・sub_cate=2）の `t_building_budget_items`＋各見積先の `t_payable_partners`（`approval_status` 未設定＝初期 `UNSELECTED`）が INSERT される。
- **ST-REG-02（グループ状態）**: 新規時に `t_building_group_statuses` が **A/B/C/D の4レコード**（`group_code` = `config('constant.building_group_codes')`、`is_completed=false`）で作成される。
- **ST-REG-03（項目グループ分割）**: `estimate_units.group`（`[["2","4"]]` 等のネスト配列/JSON）を平坦化・整数化・重複排除し、含まれるグループコード1件につき `t_building_cost_item_groups` を1レコード作成する。null/空は0件。
- **ST-REG-04（既存＝update／補完）**: 既存実行予算を **再保存**（`wasRecentlyCreated=false`）すると `update()` が走り、`source_id` 突合で既存行を UPDATE。**未登録ぶんは INSERT で補完**（見積先の遅延反映＝§13-4 ST-SYNC-03 の実体）。
- **ST-REG-05（金額はアクセサ値）**: `t_building_budget_items` の金額は生カラムでなく **アクセサ計算値**（標準単価=`master_price`／予算単価=`tmp_unit_price`／確定見積=採用業者 `adoption_flg=1` の `last_price`）を丸めて投入。採用業者が無ければ `quotation_amount=null`。
- **ST-REG-06（タイムスタンプ写像）**: `created_at`/`updated_at` は移行元の値を写す（update 時 `created_at` は温存し `updated_at` のみ更新）。
- **ST-REG-07（区画コード）**: `t_buildings.division_code` は `estimate → _tmp_budget → _division(land_units) → division` 由来。無ければ空文字。
- **ST-REG-E01（対象外項目）**: step=2・sub_cate=2 **以外** の `estimate_units` は `targetUnits()` で除外され、`t_building_budget_items` に同期されない。
- **ST-REG-E02（論理削除）**: `EstimateUnit`/`EstimateUnitCompany` は SoftDeletes のため **論理削除済みは自動除外**され同期対象外。
- **ST-REG-E03（例外＝ロールバック＆再送出）**: `register` は内部 TX。同期途中で例外が起きると **全ロールバック**し `Log::error`（`message`/`t_building_id`/`is_creating`/`file`/`line`/`trace`）を残して **再送出**する。→ felix_total の実行予算保存自体が失敗扱いになる（§0 ST-BUDGET-E02）。
- **ST-REG-E04（estimate 不在）**: 指定 `estimateId` の `Estimate` が無ければ何もせず return。

### 16-2. 項目追加 → 単体登録（`registerAddCostItemWithRelations`）

- **ST-REG-08（項目追加同期）**: 工程追加（`quickStore`）で追加された `estimate_unit`（step=2・sub_cate=2）1件について、`t_building_budget_items`＋`t_building_cost_item_groups`＋紐づく見積先の `t_payable_partners` を INSERT する（§13-4 ST-SYNC-01 の実体）。
- **ST-REG-E05（対象外/建物未登録はスキップ）**: 追加項目が step=2・sub_cate=2 以外、または対象実行予算が `t_buildings` に未同期（`source_id=estimate_id` 不在）の場合は **何もしない**（§13-4 ST-SYNC-04 / ST-SYNC-06）。

### 16-3. 見積タブ編集 → 反映（`syncCostItemIsEnabled` / `syncCostItemName`）

- **ST-REG-09（有効フラグ）**: 見積タブで項目の `use_flg` をトグルすると、`source_id`（=`estimate_units.id`）で突合した `t_building_budget_items.is_enabled` が一括更新される。
- **ST-REG-10（項目名）**: 項目名のインライン編集で `t_building_budget_items.item_name` が更新される。
- **ST-REG-E06（空配列）**: `syncCostItemIsEnabled` に空配列を渡すと何もしない。

### 16-4. 見積依頼送信 → 依頼記録（`NewCostQuotationRequestRegisterService`）

- **ST-REG-11（依頼記録）**: 見積依頼を送信すると、対象見積先（`estimate_unit_companies.id`）配下の `estimate_order_histories` を全件 `source_id` 突合で upsert し、`t_payable_quotation_requests`（`requested_at`=履歴 `created_at`）へ同期する。
- **ST-REG-12（バッチ/手動 両方）**: 依頼送信バッチ（`auto_notice_send_mail estimate`）と手動依頼の **どちらの契機でも** 同期が走る。
- **ST-REG-E07（親未登録＝スキップ）**: 親の `t_payable_partners`（`source_id`=EUC.id）が未登録なら、**依頼を紐づける土台が無い**ため同期をスキップし `Log::warning` を残す（親の作成は本サービスの責務外）。
- **ST-REG-E08（失敗は非再送出）**: 同期途中の例外は内部 TX でロールバックし `Log::error` を残すが **再送出しない**（旧テーブルの見積依頼保存は既にコミット済みで、それを妨げない）。

### 16-5. 業者マイページ保存 → 履歴・明細（`NewCostQuotationHistoryRegisterService`）

- **ST-REG-13（履歴同期）**: 業者が相見積を保存すると、type=1 の `estimate_unit_company_files` を `source_id`（=`file.id`）突合で `t_payable_quotations` へ upsert する（`file_url`/`quotation_date`(NOT NULL は作成日で補完)/`amount_excluding_tax`(null→0)/`tax_adjust`/`withholding_income_tax`/`comment`(null→空文字)）。
- **ST-REG-14（明細洗い替え）**: 各ファイル配下の `cost_unit_estimate_units`（**論理削除済みも `withTrashed` で取得**）を `t_payable_quotation_details` へ upsert し、旧側で論理削除された明細は **新側も `deleted_at` を合わせる**（洗い替え・冪等）。`price` は `genka` アクセサ（未入力時 `genka_unit * amount`）。
- **ST-REG-15（税の分割）**: 旧 `cost_unit_estimate_units.tax`（`1 + 税率` の乗数。1.10=10% / 1.00=0%）から `tax_class`（`TAXABLE`/`NON_TAXABLE`）と `tax_rate`(%) を復元する。null/空は `[null, null]`。
- **ST-REG-16（is_latest 再計算）**: 保存後、当該費用見積の履歴を一旦全て `is_latest=false` にし、type=1 を **`date DESC, id DESC` の先頭1件のみ** `is_latest=true` に更新する（現行の相見積「最新」ロジックの鏡写し）。→ fix 業者選定の「回答あり」判定・相見積履歴（§0 S5 / ST-BUDGET-03）の根拠。
- **ST-REG-E09（親未登録＝スキップ）**: 親 `t_payable_partners` 未登録なら履歴・明細の土台が無いため同期スキップ＋`Log::warning`。
- **ST-REG-E10（失敗は非再送出）**: 例外は内部 TX ロールバック＋`Log::error` のみで **再送出しない**（業者側の見積保存を妨げない）。

### 16-6. 設計ファイル充足バッチ → グループ状態（`NewBuildingGroupStatusRegisterService`）

- **ST-REG-17（充足同期）**: `CheckNoEstimate` バッチが実行予算単位で、A/B/C/D 各グループの `check_file_storage` 結果を `t_building_group_statuses.is_completed` へ **true/false 両方向** で同期する（設計ファイルは建物単位で共有のためグループごとに1回評価）。
- **ST-REG-E11（前提レコード不在はスキップ）**: 建物（`t_buildings`）未登録、またはグループ状態レコードが無い場合はスキップ（レコードは実行予算作成時＝ST-REG-02 で作成済みが前提。本サービスは **UPDATE のみ**）。

### 16-7. 総合（登録処理 × fix 参照）

- **ST-REG-E12（同期の一方向性）**: 同期は **felix_total → fix 新テーブルの一方向**。fix 側の操作（承認・仮選定・コメント等）は felix_total 旧テーブルへ **戻さない**。`approval_status`/`is_drafted` は再保存でも温存される（16-0 注記）。
- **ST-REG-E13（契機の無い追加は未反映）**: 同期契機（`register` / `registerAddCostItemWithRelations` / 各 `register`）が走らない操作（例：見積依頼画面「業者追加」iframe の見積先単体追加＝`EstimateUnitCompanyController` は同期を呼ばない）は fix に **即時反映されない**（§13-4 ST-SYNC-02。実行予算再保存＝ST-REG-04 で補完される）。
- **ST-REG-LOG-01（成否ログ）**: `register` は成功時 `Log::info`（`t_building_id` 等）、失敗時 `Log::error`（`message`/対象ID/`file`/`line`/`trace`）を残す。依頼・履歴同期は成功 `Log::info`／親不在 `Log::warning`／失敗 `Log::error`。確認は felix_total 側ログ（§0 ST-BUDGET-E02）。
