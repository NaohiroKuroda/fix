## 1. 概要

- **画面名**: 【請求】見積取消申請【FELIX(担当者)→FELIX(建設部部長)】
- **区分**: 請求＝「もらい」／**新規画面**
- **mode**: `billing-cancel-request`
- **操作ロール**: 建設部担当者（`staff_role_slugs`）、administrator
- **目的**: 承認済み（`APPROVED`）の請求見積について、**発注前**に取消を部長へ申請する。
  工事でトラブルがあった時の緊急パターン、および業者へ金額の修正依頼をしたい場合に使う。

業務フロー上の位置づけ:

```
④ 見積承認（APPROVED）──▶【見積取消申請】──申請──▶ 見積取消承認 ──承認──▶ ③ 見積作成へ差し戻し
```

- **⑤ 業者が内容を確認しているタイミングで、担当者から修正依頼をしたい場合**にもこの画面を使う。
- 発注後の取消は**一次リリース対象外**（→ §9）。

## 6. 操作仕様（取消申請・1件ずつ理由必須）

### 6.1 フロー

1. 明細行の「取消申請」を押す → 理由入力モーダルが開く。
2. 理由を入力して OK（理由未入力・送信中は OK を無効化）。
3. `t_billing_partners.approval_status` を `APPROVED → CANCEL_APPLIED` へ更新する。
4. 対象項目のコメントスレッドへ `【取消申請】{理由}` を担当者の発言として自動投稿する。

### 6.2 入力

| 項目 | 必須 | 備考 |
| --- | --- | --- |
| 対象 | ○ | 行から自動設定（請求取引先ID） |
| 理由 | ○ | テキスト。コメントに記録する |

### 6.3 応答

- 成功: `back()->with('success', "取消申請を実行しました。（n件）")`
- 0件: `back()->with('error', '取消申請を実行できませんでした。対象の請求先をご確認ください。')`
- 例外: `ServiceException` → トースト

理由モーダル UI: ゴールド系配色。パートナー名を明示し「{取消申請}します」と案内する。

## 7. felix_total 連携

- 新テーブルの `approval_status` 更新のみ（現行側の状態は取消承認時にまとめて戻す想定）。
- **業者への連絡**: もらいは**業者が既に承諾済み**のケースがあるため、申請時に業者へ連絡が必要。
  システムから通知するか運用（TEL）で行うかは未確定（§9）。

## 8. 共通機能の利用

- **やり取り（コメント）**: 担当者（staff）視点で発言。取消申請理由もここに残る（共通仕様 §4）。
- **iframe モーダル**: 見積先の詳細（共通仕様 §5）。
- **フィルタ**: `keyword` / `itemLabel` / `vendor` / `comment`（共通仕様 §3）。

## 8.4 画面の表示条件

> 出典: **見積管理_処理フロー**（H列 初期表示条件 / I列 絞り込み条件 / J列 表示承認ステータス /
> K列 ステータス外表示形式 / L列 業者マイページ）。

### 初期表示条件

- 区分が**請求**
- **見積が作成されている**

### 絞り込み条件

> 表の見方（処理フロー I列の記法）
> - **単一選択**（`・` 区切り）… セグメント／ラジオ。**初期値**の列が画面初期表示時の選択。
> - **チェックボックス**（`・` 区切りなし）… 単独のトグル。**初期値**が ON のものは初期表示時からチェック済み。

| 項目 | 形式 | 選択肢 | 初期値 |
| --- | --- | --- | --- |
| 区分 | 単一選択 | 全て / 請求 | **請求** |
| コメント | 単一選択 | 全て / コメントあり / コメントなし | **全て** |


> **区分の切り替え**
> - **請求**（初期値）… `t_billing_partners` の取引先だけを表示する。
> - **全て** … 請求に加えて `t_payable_partners`（支払）の取引先も**同じ一覧に並べる**。
>   支払行は承認ステータスに関わらず**表示のみ**で操作できない（サーバが `operable = false` を返す）。

### 表示する承認ステータス

| ステータス | 条件 |
| --- | --- |
| `APPROVED`（承認済） | **かつ 業者承諾日時にデータが無いこと** |

> **重要**: 業者が「発注承諾」を押した後（承諾日時あり）は取消申請できない。
> もらい運用フローの「発注後の取消は一次リリースに含めない」を、画面の抽出条件で担保する。

### 表示ステータス以外のデータの扱い

| ステータス | 挙動 |
| --- | --- |
| `DRAFT`（未申請） | 申請できない |
| `APPLIED`（申請中） | 申請できない |
| `CANCEL_APPLIED`（取消申請中） | 申請できない |
| `CANCELLED`（取消承認済） | 申請できない |

### 業者マイページ側の操作

なし。

## 8.5 操作 → データ更新先

> 出典: **見積管理_処理フロー**（G列「データ更新先」）。
> 表の「更新先」はスプレッドシートの記述をそのまま構造化したもの。現行実装との差異は下の注記に記す。

| 操作 | 更新先 |
| --- | --- |
| **取消申請** | 請求取引先（`t_billing_partners`）の承認ステータスを更新（`APPROVED` → `CANCEL_APPLIED`） |

**現行実装（モック）との差異**

- 申請理由のコメント（`t_comments`）投稿は支払側と同じ扱いにする想定（処理フローの表には記載が無い）。

## 9. 留意事項・未確定事項

- **⑪ 取消申請の時点で業者へ連絡・通知をするかどうか**（未確定）。
- **発注後の取消は一次リリースに含めない**。業者から部長宛に業者マイページから申請する想定だが、
  一次リリースでは機能を作らず、依頼が来たら**データメンテで対応**する。
  なお発注承認後に取消依頼が来た場合、見積・発注・請求の金額はすべてイコールになる。
