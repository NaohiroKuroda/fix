## 0. 前提

支払は「**業者へ相見積を依頼し、選定・部長承認を経て発注する**」フロー。
もらい（請求）と違い、**金額を出すのは業者**で、FELIX 側は依頼・選定・承認を行う。
見積先は 2026-08 のスキーマ改訂で `t_payable_partners`（支払）と `t_billing_partners`（請求）に分離された。
現行での振り分けは `estimate_unit_companies.invoice_flg`（**OFF = 支払**／ON = 請求）。

### 対象テーブル

| テーブル | 用途 | 旧（felix_total）の対応 |
| --- | --- | --- |
| `t_payable_partners` | 支払取引先（見積先） | `estimate_unit_companies`（`invoice_flg` OFF） |
| `t_payable_quotation_requests` | 見積依頼履歴（送信回数・最終依頼日時） | 対応なし（新規） |
| `t_payable_quotations` | 支払見積（版管理。`is_latest`） | `estimate_unit_company_files`（type=1） |
| `t_payable_quotation_details` | 支払見積明細 | `cost_unit_estimate_units` |
| `t_payable_orders` | 支払発注（発注書） | 対応なし（新規） |
| `t_payable_order_details` | 支払発注明細 | 対応なし（新規） |
| `t_orders` / `t_delivery_reports` / `t_invoices` | 発注・完了報告・請求の進行状態 | `orders` ほか |
| `t_comments` / `t_comment_read_timestamps` | やり取り（項目単位・請求と共通） | なし |

> 建物・項目（`t_buildings` / `t_building_budget_items`）は請求と共通。

### 承認ステータスの語彙（★フロー図との差異）

実装は **`DRAFT` → `APPLIED` → `APPROVED` → `CANCEL_APPLIED` → `CANCELLED`** を使っている
（`t_payable_partners.approval_status`。ローカル実データも同じ5値）。

フロー図に書かれた `UNSELECTED` / `STAFF_APPROVED` / `CANCEL_APPROVED` は**実装に存在しない**。
`STAFF_APPROVED` は別カラム（`t_orders.order_status` / `t_delivery_reports.report_status` /
`t_invoices.invoice_status`）で使われている語で、承認ステータスとは別物。
→ どちらを正とするかは **§D-1**。

| フロー図の表記 | 実装の値 | 意味 |
| --- | --- | --- |
| UNSELECTED | `DRAFT` | 未選定（見積依頼まで） |
| （記載なし） | `APPLIED` | 選定済み・部長承認待ち |
| STAFF_APPROVED | `APPLIED` | 同上 |
| APPROVED | `APPROVED` | 部長承認済み |
| CANCEL_APPLIED | `CANCEL_APPLIED` | 取消申請中 |
| CANCEL_APPROVED | `CANCELLED` | 取消承認済み（完了・以降どの画面にも出ない） |

### 凡例

- **CRUD**: C=登録 / R=参照 / U=更新 / D=削除（論理削除を含む）
- **状況**: ✅実装済み ／ 🔺暫定・部分実装 ／ ❌未実装 ／ ⏸一次リリース対象外
- **担当**: 新Fix＝このリポジトリ（`fix`） ／ 現行Fix＝`felix_total` 管理画面 ／ 業者MP＝業者マイページ（felix_total）

### D-1〜D-6. 補足

**D-3**. `estimate_order_histories` は見積依頼専用のテーブルではなく、駐車場の解約通知
（`NewEstimateCustomEditController.php:804`）などでも行が作られる。同期は業者ごとに全件を写すため、
これらも「依頼1回」として数えられる。ローカル実データは 54 行 / 18 取引先（すべて `source_id` あり）。
除外するなら、同期側で見積依頼由来の行だけを選ぶ条件（`estimate_unit_id` の有無など）を決める必要がある。

**D-1**. 実装が使う5値はローカル実データでも確認済み（`DRAFT` 4 / `APPLIED` 3 / `APPROVED` 5 /
`CANCEL_APPLIED` 3 / `CANCELLED` 3）。`STAFF_APPROVED` は `t_orders.order_status` などで
別の意味に使われているため、承認ステータスへ持ち込むと**同じ語が2つの意味を持つ**。
図の側を実装に合わせるのが素直（請求側も同じ5値で揃っている）。

**D-2**. 実装が発注承認で発行しているのは、発注書の内容（金額・明細）が発注実行時点で確定するため。
図どおり部長承認で作ると、発注実行・発注承認を経ずに発注書が業者へ見えることになる。
請求側は「業者が発注承諾したとき」に発行する方針に変更済みで、支払とは契機が異なる。

**D-5**. 現状、`contract_approved_at` は**読む側だけ**が実装されている
（`OrderDeliveryRepository` の `order-acceptance` モード）。書き込みは請求側にしか無い
（`BillingOrderIssueService`）。支払側は現行 `OrderController::adoption()` が
`orders.adoption_flg` / `adoption_date` を更新するだけなので、ここに1行足すのが最短。
