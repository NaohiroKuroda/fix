# 【支払】業者承諾確認 詳細設計書

> 共通の仕組み（ヘッダー / フィルタ / やり取り / iframe / テーマ / 送信・エラー方針）は
> [共通仕様_詳細設計.md](../quotations/00_共通仕様_詳細設計.md) を参照。本書は本画面固有の差分を記述する。
>
> **本画面は「見るだけ（表示のみ）」の画面**。明細のレイアウトは**支払系（見積管理）の一覧を踏襲**し、
> 操作系（選択トグル・承諾記録・取消申請）は持たない。→ §2 / §5 / §9

## 1. 概要

- **画面名**: 【支払】業者承諾確認【発注承諾済み→FELIX(担当者)】
- **区分**: 支払（FELIX が業者へ支払う側のフロー）
- **mode**: `order-acceptance`
- **操作ロール**: 担当者 / 建設部、administrator（**閲覧のみ**。更新操作は無い）
- **目的**: 業者が発注を承諾した案件を FELIX(担当者) が確認する。**確認だけを行い、画面からの更新は行わない。**

業務フロー上の位置づけ:

```
発注承認 ──▶【業者承諾確認】──▶ 完了・納品
              （表示のみ）
```

## 2. 機能説明

**本画面は表示のみ**のため、ヘッダーの一括アクションボタン・明細の選択操作は持たない。
明細から開けるのは「発注書プレビュー」と、支払系一覧と共通の「やり取り」「iframe 詳細」だけである。

前提となる一覧表示: 発注承認済み（`t_orders.order_status = 'APPROVED'`）の発注を
「実行予算 → 項目 → パートナー」の明細で一覧表示する（支払系一覧と同じ階層構造）。（→ §4, §5）

### 2.1 絞り込み・操作バーのボタン（画面上部）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 絞り込み（検索） | 実行予算名 / 項目名 / パートナー名でサーバ側フィルタし、一覧を再取得する。 | 共通仕様 §3 |
| 区分フィルタ | 支払 / 全て（→ §8.5）。 | 共通仕様 §3.3 |
| コメント有無フィルタ | 全て / コメントあり / コメントなし。 | 共通仕様 §3 |
| 承諾状態フィルタ | 全て / 承諾済み / 未承諾（`t_orders.vendor_accepted_at` の有無）。 | §4 |
| 明細を全て開く / 閉じる | 全実行予算カードの明細を一括開閉する。 | 共通仕様 §1.4 |

> **ヘッダーの一括アクションボタン（「承諾を確認」）は持たない。** 表示のみの画面のため
> `actionLabel` は `null` とする（取消系画面と同じ扱い）。

### 2.2 明細のボタン（各行）

| ボタン / 操作 | 実行される処理 | 参照 |
| --- | --- | --- |
| 発注書 | 発注書プレビューを表示する。承諾済みは「承認済」ハンコ付き。 | §6.1 |
| パートナー名（リンク） | 見積先の詳細を iframe で開く。 | 共通仕様 §5 |
| やり取り吹き出し（項目列） | コメントモーダルを開く（費用項目単位）。 | 共通仕様 §4 |

> **選択トグル（承諾確認）・取消申請ボタンは持たない。**
> 承諾は業者マイページ側の操作で自動的に記録され、本画面はその結果を表示するだけ。（→ §6.2, §7）

## 4. 表示データ・抽出条件

**発注書テーブル（`t_payable_orders`）を表示元にする。** 2026-08 のスキーマ改訂で追加されたテーブルで、
発注書1通＝1レコード。金額（税別合計）と業者の請負承認日時を持つ。
発注の**承認ステータス**（担当実行 → 部長承認 → 取消申請 → 取消承認）は引き続き `t_orders.order_status` が持つ。

| 項目 | 内容 |
| --- | --- |
| 起点 | `t_payable_partners`（`approval_status = 'APPROVED'`） |
| 抽出条件 | `t_orders.order_status = 'APPROVED'`（発注承認済み）**かつ 発注書（`t_payable_orders`）が発行済み** |
| 承諾状態フィルタ | 全て（条件なし）／承諾済み（`contract_approved_at IS NOT NULL`）／未承諾（`IS NULL`） |
| 並び順 | 支払系一覧と同じ（実行予算 → 項目（`sort`, `id`） → パートナー（`id`）） |

**列ごとの表示元**

| 列 | テーブル.カラム | 経路 |
| --- | --- | --- |
| 項目名 | `t_building_budget_items.name` | `t_payable_partners.building_budget_item_id` |
| パートナー名 | `companies.company_name` | `t_payable_partners.company_id` |
| 発注金額 | `t_payable_orders.subtotal_amount`（合計金額（税別）） | `t_payable_orders.payable_partner_id` |
| 発注承諾日 | `t_payable_orders.contract_approved_at`（請負承認日時） | 同上 |
| 発注書 | `t_payable_orders`（`issued_at` / `status` / `tax_amount` / `withholding_tax`）＋ 明細 `t_payable_order_details` | 同上 |

> **発注書の発行タイミング**: **部長の発注承認時**（`OrderDeliveryRepository::approveOrders()`）。
> 承認と同時に、その時点の最新見積（`t_payable_quotations` の `is_latest`）の金額・明細を写して
> `t_payable_orders` ＋ `t_payable_order_details` を作る。メモ行（`is_memo`）は発注書に載せない。
> 発注の**否認・取消承認**では発注書も併せて削除する。
>
> 旧 `t_orders`（`amount` / `vendor_accepted_at`）しか持たない改訂前のデータのために、
> 一覧の金額・承諾日は発注書が無ければ `t_orders` へフォールバックする。改訂前データの補完は
> マイグレーション `2026_08_31_000000_backfill_payable_orders_from_legacy_orders` で行う。

## 5. 画面レイアウト（明細テーブルの列）

**支払系（見積管理）の一覧を踏襲**し、実行予算カード → 項目 → パートナーの階層で表示する。
同一項目は項目列を rowspan でまとめる。**列は次の5つだけとし、操作列は持たない。**

| 列 | 内容 | 備考 |
| --- | --- | --- |
| 項目名 | `t_building_budget_items.name` | 項目の先頭行にのみ表示。右隣にやり取り吹き出し |
| パートナー名 | 会社名（`companies.company_name`） | 区分「全て」で逆区分の行が混ざったときは区分バッジを内包 |
| 発注金額 | `t_payable_orders.subtotal_amount`（税別） | 発注書発行時に確定した金額 |
| 発注承諾日 | `t_payable_orders.contract_approved_at` | 日付のみ（`Y/m/d`）で表示。未承諾は「—」 |
| 発注書 | 「発注書」ボタン | 押下でプレビュー（§6.1）。**唯一のボタン** |

> **標準単価 / 予算単価 / 相見積・見積 / 発注日 / 承諾期限 の列は持たない。**
> 発注後の確認画面のため、見積段階の単価は不要。金額は**発注金額のみ**を表示する。
>
> **区分列は設けない。** 区分フィルタで「全て」を選んだときは、支払系一覧と同じ区分バッジを
> **パートナー名セルの中**に表示する（列は増やさない）。逆区分の行は表示のみ（`operable = false`）。

## 6. 操作仕様

### 6.1 フロー

本画面に更新フローは無い。一覧を表示し、必要に応じて発注書プレビュー・やり取り・見積先詳細を開くだけ。

- 「発注書」ボタン押下 → felix_total の発注書確認画面（`check_company_list`）を iframe で開く
  （`config('felix.order_document_url')`。物件＝`t_buildings.source_id` で絞り込む）。
  発注実行・発注承認画面の「発注書」ボタンと同じ仕組み。
- 業者が承諾済みの場合は**「承認済」のハンコ**が押された状態で表示される（felix_total 側の描画）。
- 物件に移行元（`source_id`）が無い場合は URL を組めないため「—」を表示する。

### 6.2 入力

なし（表示のみ）。チェックボックス・トグル・理由入力モーダルはいずれも持たない。

### 6.3 処理

なし（GET のみ。更新系エンドポイントを持たない）。
発注承諾日は業者マイページ側の操作を受けてシステムが記録する。（→ §7）

### 6.4 応答

- 成功: 一覧を表示する。
- 0件: 「該当するデータがありません」を表示する。
- 例外: `ServiceException` → トースト。

## 7. felix_total 連携

- 連携の要否: **画面からの更新は無い**（本画面は表示のみ）。
- 「発注承諾」は業者マイページ（felix_total）側の操作。承諾されると `t_orders.vendor_accepted_at` が
  記録され、本画面の「発注承諾日」に反映される。連携方式（API / DB 直参照）は **TBD**。

## 8.5 画面の表示条件

> 出典: **見積管理_処理フロー**（H〜L 列）。

### アクション

**現時点では次にすべきアクションが無いため表示のみ。**
処理フロー上に「それなら例の『ステータス確認』画面で足りるかも？」というコメントがあり、
**独立画面として残すか、ステータス確認画面へ統合するかは未決**（→ §9）。

### 初期表示条件

- 区分が**支払**
- **選定業者を承認**（部長承認済み）

### 絞り込み条件

> 表の見方（処理フロー I列の記法）
> - **単一選択**（`・` 区切り）… セグメント／ラジオ。**初期値**の列が画面初期表示時の選択。
> - **チェックボックス**（`・` 区切りなし）… 単独のトグル。**初期値**が ON のものは初期表示時からチェック済み。

| 項目 | 形式 | 選択肢 | 初期値 |
| --- | --- | --- | --- |
| 区分 | 単一選択 | 全て / 支払 | **支払** |
| コメント | 単一選択 | 全て / コメントあり / コメントなし | **全て** |


> **区分の切り替え**
> - **支払**（初期値）… `t_payable_partners` の取引先だけを表示する。
> - **全て** … 支払に加えて `t_billing_partners`（請求）の取引先も**同じ一覧に並べる**。
>   請求行は承認ステータスに関わらず**表示のみ**で操作できない（サーバが `operable = false` を返す）。
>   ただし本画面は支払行も含めて全行が表示のみのため、区分による操作可否の差は生じない。

### 表示する承認ステータス

| ステータス | 条件 |
| --- | --- |
| `APPROVED`（承認済） | かつ **発注テーブルにデータがあること** |

### 表示ステータス以外のデータの扱い

**それ以前のステータスのデータは見積管理側に表示し、本画面には出さない。**
＝ 見積管理と発注管理でデータが重複して見えないよう、ステータスで担当画面を分ける。

### 業者マイページ側の操作

なし（請負承認は部長承認後の発注書画面で行う。
→ [03_支払_部長承認](../quotations/03_支払_部長承認_詳細設計.md) §7.4）。

## 9. 留意事項

- **本画面を表示のみに変更した（本改訂・実装済み）。** 次の機能は**廃止**した。
  - 明細の選択トグル（承諾確認）と、ヘッダー一括ボタン「承諾を確認」（`POST /order-delivery/order-acceptance`）
  - 明細の「取消申請」ボタン（`POST .../cancel-request`）と「再通知」（`POST .../renotify`）
    → 発注の取消は [発注取消申請] 画面から行う。
  - 発注日列・区分列（列は §5 の5列に揃えた）
- **承諾を FELIX 側から記録する手段は無くなった。** `contract_approved_at` は業者マイページ
  （felix_total）側の操作で入る想定で、連携方式は **TBD**（§7）。
  そのため、後続の完了確認（`t_orders.vendor_accepted_at` を条件にする）へ進めるデータは
  当面できない。連携が入るまではデータメンテで日時を入れて確認する。
- 「請求（もらい）」側の対になる画面は [02_請求_発注書確認](./02_請求_発注書確認_詳細設計.md)。
  明細の列構成は本画面と揃えている。
