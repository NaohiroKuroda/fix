# AI 開発コンテキスト & 設計指示書

## 1. プロジェクト概要 & 全体アーキテクチャ方針
本プロジェクトは、現行システム（Laravel 8 + laravel-admin）から、データベースを共有した状態での段階的な新システムへの移行プロジェクトである。
バックエンド（Laravel 13）およびフロントエンド（Inertia.js + Vue 3）ともに完全新規で構築する。

新システムでは、Laravel 13 の薄い Controller、ビジネスロジックをカプセル化する Service Layer、リクエストデータの堅牢な型安全性を担保する Data/DTO Layer、表示データを成形する JsonResource、およびフロントエンドの Inertia.js 3.x (Vue 3) を組み合わせた、完全型安全（Type-Safe）なアーキテクチャを採用する。各層の責務を厳格に分離し、PHP 8.3 および TypeScript の仕様を最大限活かした保守性の高いコードを生成すること。

## 2. 出力時の共通留意事項（AI への基本命令）
* **PHP 8.3 の厳格な型付け**: 生成するすべてのバックエンドコードにおいて、引数・戻り値の型、プロパティのプロモーション（Constructor Promotion）を徹底すること。
* **動的プロパティの禁止**: クラスに定義のない変数の動的生成は PHP 8.2 以降で非推奨・禁止されているため、一切出力しないこと。
* **TypeScript の厳格化**: フロントエンドにおいて `any` の使用は原則禁止。型定義（Interface/Type）を明示すること。LaravelからInertia経由で渡される Props の型は必ず定義すること。

## 3. 段階的移行における最重要ルール（並行稼働・既存DB共有）
* **既存DB整合性の絶対死守**: 新システム側でのデータ更新・参照は、既存システム（Laravel 8）のデータベーススキーマ、および既存データの整合性を絶対に破壊してはならない。
* **未実装機能のルーティング制限**: 新システムで未実装の機能・画面については、現行システム（Laravel 8）側へリダイレクトまたはプロキシ経由で処理を逃がす運用となる。新システム側のルート定義やメニュー生成時は、この併用状態（URL設計など）に配慮すること。
* **破壊的変更の警告**: 既存の Laravel 8 側の仕様やDBに影響を与えそうな破壊的変更を検知した場合は、コード生成前に必ずユーザーに警告し、確認を促すこと。

## 4. 各レイヤーの責務と配置ルール
### 4.1 フロントエンド（Vue 3 / Inertia.js 3.x）
* **役割**
	* UIのレンダリングおよびユーザー入力のハンドリング。
	* Inertia フォーム（`useForm`）によるリクエスト送信およびSPA状態の管理。
* **使用パッケージ（composer）**
	* `laravel/wayfinder`
* **使用パッケージ（npm）**
	* `@inertiajs/vue3`（3.0以上）
	* `dayjs`
	* `reka-ui`
	* `vue`（3.5以上）
	* `@laravel/vite-plugin-wayfinder`（開発環境のみ）
	* `@tailwindcss/vite`（開発環境のみ）
	* `laravel-vite-plugin`（開発環境のみ）
	* `typescript`（開発環境のみ）
	* `vite`（開発環境のみ）
	* `tailwindcss`（開発環境のみ、4.0以上）
	* `shadcn-vue`
* **ルール**
	* **SFC（Single File Component）の徹底**: 必ず `<script setup lang="ts">` を使用すること。Options API（`data()`, `methods` 等）は全面禁止。
	* **JSX / TSX の全面禁止**: 将来的な Vue 3.6 Vapor モード（仮想DOMに依存しないコンパイル戦略）へのスムーズな移行を見据え、JSX/TSX および `render()` 関数によるコンポーネント記述は全面禁止とする。UIは必ず `<template>` タグを用いたHTMLライクな構文で記述すること。
	* **ロジックの排除**: ビジネスロジックや高度なデータ加工は行わず、Props から受け取ったデータをそのまま表示すること（加工は JsonResource 層で行う）。
	* **スタイル定義の制限**: `.vue` ファイルの `style` ブロック、およびコンポーネント内要素への `style` 属性（インラインスタイル）の直接指定は全面禁止。
	* **リアクティビティの最適化**: `ref()` と `computed()` を適切に使い分けること。高頻度なイベント（マウス移動、キャンバス操作等）が発生する箇所では、オブジェクトの再生成を避け、ガベージコレクション（GC）負荷を最小限に抑えるクリーンなコードを書くこと。
	* **Inertia 固有機能の利用**: フォーム送信時は必ず Inertia の `useForm` を使用し、送信状態（`processing`）やエラー（`errors`）を統合管理する。ページ遷移は `Link` コンポーネントを使用し、ルーティングには Ziggy の `route('name')` を使用して URL のハードコーディングを禁止する。
	* **Laravel Wayfinder による完全型安全なルーティングの徹底**: 
		* 画面遷移、APIリクエスト、およびフォームの送信先におけるURL文字列（パス）のハードコーディング、および文字列によるルート名指定は一切禁止。
		* ルーティングの指定には、必ず `laravel/wayfinder` が自動生成した型安全な関数・メソッド（例: `routes.auth.login()` など）を使用すること。
		* バックエンド側で定義されたコントローラーのアクション、引数、および返却されるPropsの型定義と、フロントエンドの呼び出しが型レベルで100%一致している状態を維持すること。

### 4.2 コントローラー層（Controller）
* **役割**
	* HTTPリクエストの受付、認証情報の紐付け、Serviceの呼び出し、および Inertia レスポンスの返却。
* **使用パッケージ**
	* なし（Laravel 標準）
* **ルール**
	* **「薄いコントローラー（Skinny Controller）」の徹底**: 条件分岐やDB操作（Eloquentの直接呼び出し）は一切禁止。
	* **データの引き渡し**: リクエストデータは後述の Data/DTO 層を介して Service へ渡し、フロントへの返却データは必ず JsonResource を使用して成形する。

### 4.3 データ・バリデーション層（Data / DTO）
* **役割**
	* 外部からの入力データのバリデーション（型・必須チェック）およびサービス層へ渡すデータの構造化・型定義。
	* 入力データに形式的な瑕疵がある場合は、自動で `422 Unprocessable Entity` を返却する。
* **使用パッケージ**
	* `spatie/laravel-data`
* **ルール**
	* **FormRequestの禁止**: 従来の `FormRequest` と連想配列（`array`）の組み合わせは型安全性が失われるため禁止とする。
	* **型付きオブジェクトの強制**: `spatie/laravel-data` を用いた `Data` クラスを採用し、コントローラーからサービス層へは必ず型付けされたオブジェクト（DTO）としてデータを引き渡すこと。
	* **検証範囲の制限**: ビジネスロジックが絡む動的な検証（例: 特定のステータス時のみ許可など）はここでは行わない。

### 4.4 サービス層（Service）
* **役割**
	* システムの核心となるビジネスロジック（ドメインルール）の実行、およびユースケースの表現。
* **使用パッケージ**
	* なし（インフラ層などの必要に応じて各種外部パッケージ）
* **ルール**
	* **クラスの集約**: 原則として1つのアクション（または1つのドメイン）に対して1つの Service クラス、または同一ドメインの複数メソッドとして集約する。
	* **入力の制限**: 常に型付きの Data/DTO オブジェクトを受け取る構造にすること。
	* **再利用性の担保**: Controller に依存せず、CLI（Artisanコマンド）や Queue（非同期ジョブ）からも全く同じロジックを再利用できる構造にすること。
	* **トランザクション制御**: データベースのトランザクション管理（`DB::transaction` 等）は、すべてこの層の責務とする。

### 4.5 データベース・モデル層（Model）
* **役割**
	* データの永続化、およびリレーションやスコープの定義。
* **使用パッケージ**
	* `barryvdh/laravel-ide-helper` （開発環境のみ）
* **ルール**
	* **PHPDoc による型定義の強制**: 
	    * すべてのモデルは `php artisan ide-helper:models -W` を実行し、DBカラムやリレーション、ローカルスコープの型アノテーション（PHPDoc）をファイルヘッダーに直接書き込むこと。
		* Claude Code を含むすべてのAIおよび静的解析ツールは、このPHPDocに記載された型情報を正原則として信頼してコードを生成すること。
	* **ロジックの排除**: モデル内にはビジネスロジックを一切書かない。
	* **厳格なキャスト定義**: 以下のカラムは、新設された casts() メソッド内で明示的に型キャストを定義すること。
		* `BOOLEAN` 型のカラム
		* `DATE` 型のカラム
		* 独自に定義した `DATETIME` 型、`TIMESTAMP` 型のカラム
	* **クエリの共通化**: ステータス等の特定の絞り込みがある場合は、必ずローカルスコープを定義すること。
	* **リレーションの最適化**: ステータス等の絞り込みを伴うリレーションは、Eager Loading（`with`）が可能となるよう、専用の名前付きリレーションを個別に定義すること。

### 4.6 表示・成形層（JsonResource）
* **役割**
	* データベースの構造（生データ）を、フロントエンド（Vue 3）が求める最適なデータ構造（JSON）へと変換・成形する。
* **使用パッケージ**
	* なし（Laravel 標準）
* **ルール**
	* **表示ロジックの集約**: 現行システムでビュー（Blade等）側で行われていた複雑な表示ロジック、文字列加工、関連データの集計ロジックは、すべてこの JsonResource 内に集約すること。

## 5. Claude Code への出力要求（プロンプトガイドレール）
* **規約の絶対遵守**: コードを生成または修正する際は、常に上記の「技術スタック」「出力時の留意事項」「各レイヤーのルール」を遵守すること。
* **レビュー親和性の担保**: 本アーキテクチャの未経験者がコードレビューを行うことを前提とし、特に複雑なカスタムコンポーザブルや、DTO・Service間のデータフローを生成した場合は、コードコメントで「なぜその実装にしたのか（型安全性やメモリ効率の意図）」を日本語で明記すること。
